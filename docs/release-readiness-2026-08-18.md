## 2. Мерж не будет fast-forward — и это не проблема

`git merge-base --is-ancestor main develop` **не проходит**: на `main` есть **3** коммита,
которых нет на `develop` — хотфикс воскресной недели (`ed69712`), его merge-коммит и
`0ab11c2 docs: sync docs/ from develop to main`.

Проверено, что хотфикс **не откатится**: `web/src/lib/calendar/weekRange.ts` существует на
`develop`, `computeWeekRange` там вызывается из `Calendar.tsx:97`, а старой строки
`getDay() + 1` на `develop` нет вовсе.

Пробный мерж (`git merge-tree --write-tree main develop`):

- `web/src/pages/Calendar/Calendar.tsx` — **auto-merge, без конфликта**;
- конфликтуют ровно **5 файлов, и все — документы** (add/add, следствие того самого
  `docs: sync`): три плана и две спеки из `docs/superpowers/` за июнь.

Разрешение механическое: брать версию `develop` (она новее — на `main` они попали копией).
**Кода в конфликтах нет.**

## 3. Разрушительная миграция — доказано безопасна

Из семи применяемых данные пишут три:

| Миграция | Что делает с данными | Риск |
|---|---|---|
| `000010_add_reminders` | `UPDATE reminder SET source_kind …` | нет, дозаполнение |
| `000012_calendars` | `INSERT` личного календаря каждому + `UPDATE event/task` | нет, backfill |
| `000013_exception_unique_per_series` | 🔴 **`DELETE FROM event_exception` + `DELETE FROM event`** | см. ниже |

`000013` схлопывает дубли `(event_id, occurrence)` перед уникальным индексом и удаляет замены
проигравших строк. Проверено на **проде**, а не предположено:

```sql
SELECT count(*) FROM (
  SELECT event_id, occurrence FROM event_exception GROUP BY 1,2 HAVING count(*) > 1
) d;   -- → 0
```

Больше того, `event_exception` на проде **пуста целиком**. Состояние прода на 18.08:
**6 пользователей · 23 события · 0 исключений · 7 задач**. То есть `DELETE` в `000013` —
no-op, удалять нечего.

## 3.5. Перестройка уникального индекса — тоже доказана, и это НЕ то же самое

🔴 Едва не засчитал §3 за проверку всего разрушительного. `000015_reminder_calendar`
**перестраивает `idx_reminder_dedupe`** — уникальный индекс с `NULLS NOT DISTINCT` — поверх
уже существующей таблицы `reminder`. Дубли там я не считал, а комментарий в `000010` говорит
дословно: таблица *«believed empty in production»*. Вера — не состояние
(`learning-a-mechanism-is-not-a-state`).

Отказ здесь страшнее потери данных: если построение индекса падает, golang-migrate ставит
`schema_migrations.dirty = true` и **отказывается работать дальше** — API уходит в crash-loop.
К этому моменту деплой уже сделал `docker compose down`, а `curl /api/health || exit 1` лишь
констатирует труп. Лечится руками, бэкап тут не помогает.

Проверено на проде:

```sql
SELECT to_regclass('public.reminder') IS NOT NULL;  -- → t, таблица есть
SELECT count(*) FROM reminder;                      -- → 0
```

Ноль строк → столкновение по уникальному ключу невозможно, `000015` механически безопасна.
