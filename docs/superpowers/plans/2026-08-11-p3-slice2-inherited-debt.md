# P3 срез 2 — что унаследовано осознанно

> Составлено 11.08.2026 по итогам финального ревью среза 1. Это не план, а **список входных
> условий** для следующего среза: что оставлено сознательно, почему это не было дефектом среза 1
> и где именно оно проявится, когда у календаря появится второй участник.
>
> Спека: `2026-08-11-p3-shared-calendars-design.md` · План среза 1:
> `2026-08-11-p3-slice1-calendar-foundation.md`

## Почему это не долг «по недосмотру»

Срез 1 обещал одно: **доступ к событиям и задачам определяется членством в календаре, и снаружи
не меняется ничего**. Обещание выполнено — 57 событий из 57 и 8 задач из 8 на staging видны через
новый механизм, e2e совпал с базовой линией.

Всё ниже недостижимо, **пока у каждого календаря ровно один участник**. Чинить это в срезе 1
означало бы писать код без единого сценария, на котором его можно проверить.

## 1. 🔴 Роли не проверяются нигде

`calendars.AccessibleIDs` (`api-go/internal/calendars/access.go`) фильтрует членства по `status`,
но **не по `role`**. Пока участник один и он `owner`, разницы нет. С появлением `viewer` он
сможет писать во всех перечисленных местах:

| Путь | Что сделает viewer |
|---|---|
| `events/handlers.go` `updateEvent` | правит любое поле общего события |
| `events/handlers.go` `deleteEvent` | удаляет общее событие целиком |
| `events/handlers.go` `moveEvent` / `resizeEvent` | двигает и растягивает |
| `events/handlers.go` `addException` | удаляет одно вхождение общей серии |
| `events/occurrence.go` `detachOccurrence` | пишет новое событие **в чужой календарь** |
| `tasks/handlers.go` `updateTask` / `deleteTask` | правит и удаляет общую задачу |
| `tasks/handlers.go` `scheduleTask` | создаёт событие в календаре задачи |
| `tasks/handlers.go` `logTaskTime` | меняет `actual_minutes` |
| `reminders/action.go` | 🔴 закрывает общую задачу **кнопкой в Telegram**, мимо веба вообще |

Последняя строка отдельно: это единственный путь записи, не проходящий через веб-интерфейс, и
про него легче всего забыть, добавляя проверку роли.

## 2. 🔴 Напоминания у общего события будут одинаковыми у всех

Спека §1 обещает «каждому своё». Это станет правдой только в **срезе 5**, когда появятся
`event_reminder` / `task_reminder` (спека §4.2).

До тех пор `reminder_offsets` — **одно поле на событие**, а сканер (`reminders/scan.go`) читает
его для каждого участника календаря. Следствия:

- у обоих участников напоминания одинаковые;
- любой `updateEvent` от второго участника **молча перезаписывает** смещения первого;
- ручки `PUT /api/events/:id/reminders` (спека §8) не существует.

Это не дефект реализации, а порядок срезов. Но если срез 2 включает расшаривание, а срез 5 ещё
не сделан — пользователи получат ровно это поведение, и лучше сказать им заранее, чем чинить
жалобу.

## 3. Дубли при отцеплении вхождения общей серии

`event_exception` уникален по `(user_id, event_id, occurrence)`, а чтение исключений теперь идёт
по календарю. Два участника, правящие **одно и то же** вхождение, создадут две строки исключения
и два замещающих события — оба видимые обоим.

## 4. Подзадача уезжает из общего календаря

`tasks/handlers.go` `createTask` безусловно берёт `PersonalIDFor`, а `parent_id` пишет как
пришёл. Родитель в общем календаре — ребёнок в личном; второй участник увидит родителя без
ребёнка. То же при перепривязке `parent_id` в `updateTask`.

## 5. Экспорт как канал массовой выгрузки чужого

`GET /api/export` отдаёт содержимое **всех доступных** календарей одним файлом и ролью не
ограничен. В срезе 1 это тождественно старому поведению (календарь один), в срезе 2 это
единственный путь выгрузить чужое целиком.

⚠️ **Асимметрию в `export/queries.go` не «чинить».** Экспорт намеренно **не** выбирает
`calendar_id` — именно поэтому импорт физически не может стать записью в чужой календарь. Тот,
кто придёт выравнивать это с остальными ответами, откроет дыру. Комментарий стоит в
`export/handlers.go`.

## 6. Режим «занят/свободен» объявлен, но не читается

`calendar_member.visibility` ('full' / 'busy') есть в схеме с миграции 000012, но
`AccessibleIDs` его не смотрит. Когда режим включат, все пути чтения — включая `export` и
утренний дайджест — отдадут названия целиком.

## 7. Мелочи, не влияющие на корректность сегодня

- **N+1 на `calendar_member`.** `events/recurrence.go` зовёт `CalendarIDsFor` внутри цикла по
  событиям; `reminders/scan.go` делает правильно — читает список один раз и протягивает
  параметром. Образец уже в репозитории, перенос механический.
- **Две формы обхода охранного теста остались открытыми** сознательно: `INSERT INTO event
  VALUES (...)` без списка колонок и SQL, собранный через `fmt.Sprintf` в двойных кавычках. Ни
  одному существующему запросу не соответствуют.
- **`fetchExceptions` глотает ошибку** в «исключений нет» — удалённые вхождения снова появятся в
  календаре. Путь редкий, сигнатура не возвращает `error`, дефект пре-существующий.
- **`digestEvents` / `digestTasks` глотают ошибку запроса**, а `insertDigest` всё равно пишет
  строку с `ON CONFLICT DO NOTHING` — «навсегда пустой дайджест», который правильный уже не
  заменит. Уровнем выше от этого защищается `continue`, внутри — нет.
- **`PersonalIDFor` сравнивает ошибку через `!=`, а не `errors.Is`** — обёрнутая ошибка пройдёт
  мимо ветки восстановления и вернётся как 500.

## 8. 🔴 Слияние личностей: скрипт теперь обязан переносить календарь

Предусловие P3 (спека §10.0). После миграции 000012 наивный скрипт

```sql
UPDATE event SET user_id = A WHERE user_id = B;
DELETE FROM "user" WHERE id = B;
```

**упадёт**: `calendar.owner_id` каскадится от `"user"`, а `event.calendar_id REFERENCES
calendar(id)` объявлен без `ON DELETE`. Каскад попытается снести календарь B, на который ещё
смотрят строки `event` и `task`.

Правильный порядок — до удаления пользователя:

```sql
UPDATE event SET calendar_id = <personal(A)> WHERE calendar_id = <personal(B)>;
UPDATE task  SET calendar_id = <personal(A)> WHERE calendar_id = <personal(B)>;
DELETE FROM calendar_member WHERE calendar_id = <personal(B)>;
DELETE FROM calendar        WHERE id          = <personal(B)>;
```

⚠️ Что **не проверено и утверждать нельзя**: что сделает голый `DELETE FROM "user" WHERE id = B`
без предшествующего `UPDATE`. Там сталкиваются два каскада, и порядок обработки внешних ключей
между несколькими ссылающимися таблицами из чтения схемы не выводится. **Проверять на копии
прода, а не рассуждением.**
