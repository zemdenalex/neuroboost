# Окно событий календаря: ±1 промежуток вместо недели

**Статус:** черновик на ревью Дениса · **Дата:** 2026-09-11
**Первопричина:** `docs/defekty-sreza-1-2026-09-10.md` §1б+4б
**Свидетельство:** `ref/feedback/prohod-sreza-1-otvet-denisa-2026-09-10.md`
**Выбрано Денисом** 11.09 после приёмки v0.4.11 как фокус v0.4.12.

## Откуда взялась

Денис, 10.09: *«День меняется, но всё ещё не загружает события каждый день, только на
неделю если долистать до понедельника»* и *«если промотать вперед до следующей недели,
а потом обратно назад — события исчезают»*.

Это **один** дефект, а не два. Данными и экраном управляют разные счётчики:

- `Calendar.tsx:137` грузит **неделю** по `currentWeekOffset`;
- `WeekGrid.tsx:45-49` рисует **окно из `visibleDays` дней** от
  `mondayUtc0 + mobileDayOffset * DAY_MS`, и `mobileDayOffset` живёт **внутри грида**;
- мирит их единственный эффект `WeekGrid.tsx:65-76`, срабатывающий только на границе недели.

Поэтому листание назад показывает **до шести дней подряд** из недели, которую никто не
грузил. А второй эффект (`:61-63`) сбрасывает позицию при каждой смене недели, отменяя
приземление первого.

🔴 **Подпорка стояла под раздвоенным владением.** Чинить надо владение, а не подпорку.

## Что считается сделанным

1. Свайп по дням на телефоне показывает события **каждого** дня, в обе стороны.
2. Стрелка недели на десктопе вперёд-назад не теряет события.
3. День, который ещё грузится, **отличим** от дня, где событий нет.
4. День, который **не загрузился**, отличим от обоих.

## Решения Дениса (11.09)

| Вопрос | Ответ |
|---|---|
| Что такое «промежуток» | **Видимое окно**: 1 день на телефоне, 3 на планшете, 7 на десктопе |
| Меняем ли десктоп | **Да, одна модель везде.** Стрелка недели становится мгновенной |
| Как выглядит грузящийся день | **Скелет в колонке.** Никакого спиннера на весь экран — это был C7 |
| Где живёт позиция | **Хук `useEventWindow`.** `WeekGrid` становится управляемым |

Его же слова про поведение, принятые как требование: *«прогружать события промежутков до
и после, и при свайпе обновлять: если свайпаем влево, то четверг отгружается и
подгружается понедельник»*.

# Архитектура

## Якорь вместо двух счётчиков

Сегодня позицию описывают **две** переменные — `currentWeekOffset` (у страницы) и
`mobileDayOffset` (у грида). Обе уходят. Вместо них — **якорь**: UTC-миллисекунды
локальной полуночи **первого видимого дня**.

```
anchor ──────────┐
                 ▼
   [ -visibleDays ][ видимое окно ][ +visibleDays ]
   └──────────────── загружено ─────────────────┘
```

- **Видимое окно** = `[anchor, anchor + visibleDays)`.
- **Загруженный диапазон** = `[anchor - visibleDays, anchor + 2*visibleDays)` — три окна.
- **Шаг навигации** = `visibleDays`. `go('next')` → `anchor += visibleDays`.

**Начальный якорь** зависит от ширины, и это единственное место, где ширина на него влияет:

```ts
initialAnchor(visibleDays, timezone, now)
  = visibleDays >= 7 ? понедельник текущей недели : локальная полночь сегодня
```

⚠ Семидневное окно обязано начинаться с понедельника, иначе десктопная сетка перестанет
совпадать с календарной неделей. При трёх днях и одном дне выравнивания нет и не нужно:
Денис листает от **сегодня**, а не от начала недели — это и просил `initialMobileDayOffset`,
который здесь исчезает вместе со своим классом задач.

## `useEventWindow` — единственный владелец

`web/src/lib/calendar/eventWindow.ts` — чистые функции.
`web/src/hooks/useEventWindow.ts` — хук вокруг них.

```ts
const win = useEventWindow({ visibleDays, timezone })

win.anchor        // number — первый видимый день
win.events        // NbEvent[] — всё, что в загруженном диапазоне
win.loadingDays   // Set<string> — ISO-дни в полёте
win.failedDays    // Set<string> — ISO-дни, чей запрос отказал
win.go(dir)       // 'prev' | 'next'
win.goToToday()
win.invalidate()  // перечитать текущий диапазон (для возврата на вкладку, C5)
```

🔴 **Ни одного эффекта, примиряющего два состояния.** Примирять нечего: якорь один.

## Что становится глупым

`WeekGrid` перестаёт быть хозяином позиции:

| Было | Стало |
|---|---|
| `currentWeekOffset: number` (проп) | `windowStart: number` (проп) |
| `mobileDayOffset` (внутреннее состояние) | — удалено |
| два эффекта-примирителя `:61-76` | — удалены |
| `onWeekChange(offset)` | `onNavigate('prev' \| 'next')` |
| `onToday()` — сбрасывал два счётчика | `onToday()` — зовёт `win.goToToday()`, то есть `anchor = initialAnchor(...)` |
| — | `loadingDays: Set<string>` |
| — | `failedDays: Set<string>` |

🟢 **Не трогаем:** `processEventsForWeek` и `generateDays` уже принимают произвольное
начало и `visibleDays` — им всё равно, откуда пришло начало. `DayColumn`, `EventBlock`,
`AllDaySection`, перетаскивание и изменение размера не меняются вовсе.

⚠ `WeekHeader` строит подпись и навигацию от `currentWeekOffset` (`:65`, `:78`, `:92`).
Подпись выводится из `windowStart`; условие показа «сегодня» — из сравнения якоря с
`initialAnchor`.

# Данные и загрузка

## Кэш по дням, запрос по диапазонам

Кэш — `Map<ISO-день, NbEvent[]>`. Ключ дневной, потому что освобождать край надо по дням;
**запрос — по непрерывному диапазону**, потому что три запроса вместо одного на каждый шаг
превратят листание в шторм.

Шаг навигации:

1. якорь сдвигается на `visibleDays`;
2. считается новый загруженный диапазон;
3. дни вне него **выбрасываются** из кэша — это «четверг отгружается»;
4. недостающие дни сливаются в непрерывные диапазоны, на каждый — один `GET /api/events`;
5. дни этих диапазонов попадают в `loadingDays` до ответа.

Многодневное событие попадает в кэш **каждого** дня, который пересекает, — иначе оно
исчезнет при выбрасывании крайнего дня. Дубли снимаются по `id` при сборке `win.events`.

## Гонка ответов — та, из-за которой «события исчезают»

🔴 Каждый запрос помечается диапазоном, за которым послан. Ответ, чей диапазон больше не
пересекается с загруженным, **отбрасывается**. Без этого быстрый свайп туда-обратно
приводит к тому, что поздний ответ старого запроса затирает свежие данные — и это ровно тот
симптом, который Денис описал словом «исчезают».

⚠ Сегодня такой защиты нет нигде: `loadEvents` в `Calendar.tsx:137-144` делает
`setEvents(data)` безусловно.

## Отказ запроса виден

День, чей запрос отказал, выходит из `loadingDays` и входит в `failedDays`. Колонка
показывает короткую строку с повтором.

🔴 Молча оставить пустую колонку **нельзя**: вся эта работа началась с того, что «ещё не
приехало» было неотличимо от «ничего нет». Отказ, притворяющийся пустотой, — тот же дефект
под другим именем.

## Возврат на вкладку (C5) продолжает работать

`shouldRefetchOnReturn` остаётся как есть; при срабатывании зовётся `win.invalidate()` —
перечитывает текущий диапазон, не трогая якорь. Порог 30 секунд не меняется.

1. **Телефон, свайп:** событие создано на завтра → свайп вперёд → блок виден. Сегодня
