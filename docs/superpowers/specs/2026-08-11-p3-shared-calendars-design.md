# P3 — Общие календари, события и задачи

> Спека. Составлена 11.08.2026 в диалоге с Денисом. Утверждён дизайн, не реализация.
> Соседи: `2026-07-27-p1-task-quick-capture-design.md`, `2026-07-27-p2-notifications-design.md`.

## 1. Задача

Дословная боль: **«девушке приходится дублировать всё руками»**. Совместное дело — ужин,
поездка, врач — сейчас заводится дважды: у него и у неё. Каждое изменение времени тоже дважды,
и второй раз обычно забывается.

Что должно стать правдой после P3:

- Совместное событие или задача заводится **один раз** и видно обоим.
- Любой из двоих может его подвинуть, переименовать, отменить.
- Напоминание приходит **каждому своё**: ему за час, ей за сутки.
- Личное остаётся личным — по умолчанию другой человек его не видит вовсе.

## 2. Что НЕ входит

Решено явно, чтобы не расползлось:

| Не входит | Почему |
|---|---|
| Режим «занят/свободен» (видеть чужую занятость без названий) | Денис попросил, но **не в первой версии**. Место в схеме зарезервировано: `calendar_member.visibility` |
| Больше двух человек в календаре | Модель это выдержит, UI и приглашения — отдельная работа |
| Общие рефлексии, планирование, помодоро | Другие сущности, другая семантика |
| Внешние календари (Google, iCal) | Отдельный проект целиком |
| Комментарии/чат внутри события | Не про исходную боль |

🔴 **Видимость чужого личного расписания в v1 отсутствует.** В диалоге сначала прозвучало
«и то и другое», затем Денис уточнил: **«в обе стороны, но только общие»**. Действует уточнение.

## 3. Главное архитектурное следствие

Сегодня в схеме **нет понятия совместности вообще**. Каждая сущность объявлена как
`user_id UUID NOT NULL REFERENCES "user"(id) ON DELETE CASCADE`, и эта же колонка отвечает
сразу за две разные вещи: **кто владелец** и **кому можно смотреть**.

P3 эти две вещи разделяет:

- **Контейнер доступа** — календарь. Кто состоит в календаре, тот видит его содержимое.
- **Авторство** — `event.user_id` / `task.user_id` остаются, но означают теперь **кто создал**.
  Право доступа они больше не дают.

Это самая рискованная часть работы: `user_id` встречается **91 раз** в `api-go/internal/`,
из них **23** в `events` и **17** в `tasks` (посчитано 11.08). Каждое из этих мест сегодня
неявно предполагает «моё = где стоит мой user_id».

🔴 **Одна точка принятия решения о доступе.** Проверку нельзя размазывать по 40 запросам —
одно забытое место означает чужие данные в чужом браузере. Вводится единственный helper:

```go
// CalendarIDsFor возвращает id всех календарей, к которым у пользователя есть доступ.
// Любой запрос событий и задач фильтрует по calendar_id IN (...), и никак иначе.
func CalendarIDsFor(ctx context.Context, userID string) ([]string, error)
```

Тест, который перечисляет handlers и требует, чтобы ни один не строил запрос по `user_id`
напрямую, — часть работы, а не пожелание (см. §9).

## 4. Данные

### 4.1. Новые таблицы

```sql
CREATE TABLE calendar (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id   UUID NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    name       TEXT NOT NULL,
    color      TEXT,
    kind       TEXT NOT NULL CHECK (kind IN ('personal','shared')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE calendar_member (
    calendar_id UUID NOT NULL REFERENCES calendar(id) ON DELETE CASCADE,
    user_id     UUID NOT NULL REFERENCES "user"(id)   ON DELETE CASCADE,
    role        TEXT NOT NULL CHECK (role IN ('owner','editor','viewer')),
    -- Зарезервировано под «занят/свободен». В v1 всегда 'full'.
    visibility  TEXT NOT NULL DEFAULT 'full' CHECK (visibility IN ('full','busy')),
    status      TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('invited','active')),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (calendar_id, user_id)
);
```

### 4.2. Напоминания переезжают на связку «сущность + человек»

🔴 Это правка того, что построено в P2. Сегодня `event.reminder_offsets` — **одно поле на
событие**, то есть общее для всех, кто его видит. Требование Дениса — «у каждого свои».

```sql
CREATE TABLE event_reminder (
    event_id UUID NOT NULL REFERENCES event(id) ON DELETE CASCADE,
    user_id  UUID NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    offsets  INTEGER[] NOT NULL,
    PRIMARY KEY (event_id, user_id)
);

CREATE TABLE task_reminder (
    task_id UUID NOT NULL REFERENCES task(id) ON DELETE CASCADE,
    user_id UUID NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    offsets INTEGER[] NOT NULL,
    PRIMARY KEY (task_id, user_id)
);
```

**Два слоя, не три:**

1. Есть моя строка в `event_reminder` → работают её `offsets`.
2. Строки нет → берётся мой пресет из настроек (`usersettings`, уже существует).

Слой «умолчание календаря» рассматривался и **выброшен**: он давал третье место, куда надо
смотреть при разборе «почему не пришло напоминание», ради удобства, которое закрывается
пресетом в настройках.

⚠️ Пустой массив `[]` по-прежнему значит «намеренно без напоминаний» и **не** то же самое,
что отсутствующая строка. Это правило уже действует в P2 и здесь сохраняется.

### 4.3. Изменения существующих таблиц

```sql
ALTER TABLE event ADD COLUMN calendar_id UUID REFERENCES calendar(id);
ALTER TABLE task  ADD COLUMN calendar_id UUID REFERENCES calendar(id);
-- после бэкфилла (§7):
ALTER TABLE event ALTER COLUMN calendar_id SET NOT NULL;
ALTER TABLE task  ALTER COLUMN calendar_id SET NOT NULL;

CREATE INDEX idx_event_calendar_time ON event (calendar_id, starts_at);
CREATE INDEX idx_task_calendar       ON task  (calendar_id);
```

`event.reminder_offsets` и `task.reminder_offsets` после миграции **не читаются**. Колонки не
удаляются в этой версии: пока новый путь не отработал на живых данных, старое значение —
единственный способ восстановить смещения, если бэкфилл окажется неверным.

## 5. Права и доступ

| Роль | Может |
|---|---|
| `owner` | всё, включая переименование и удаление календаря, приглашение и исключение участников |
| `editor` | создавать, править и удалять события и задачи внутри календаря |
| `viewer` | только смотреть |

В v1 используются `owner` и `editor`: личный календарь — один `owner`; общий — создатель
`owner`, приглашённый `editor`. `viewer` объявлен в схеме, потому что он понадобится вместе с
режимом «занят/свободен», и вводить его потом отдельной миграцией дороже, чем объявить сразу.

### 5.1. Удаление — единственное место, где легко потерять чужое

🔴 `calendar_member` каскадится по календарю, а **события каскадиться не должны**: удаление
общего календаря иначе уносит события обоих людей, включая те, что завёл не удаляющий.

Правило: **удалить общий календарь можно только пустым.** Попытка удалить непустой возвращает
`409 CALENDAR_NOT_EMPTY` со счётчиком того, что внутри. Пользователю предлагается перенести
содержимое в свой личный календарь одним действием.

Исключение участника (`DELETE /calendars/:id/members/:userId`) — не удаляет события, которые он
создал: они остаются в общем календаре. Удаляются только его строки в `event_reminder` /
`task_reminder`: напоминания человеку, потерявшему доступ, слать нельзя.

## 6. Напоминания: что меняется в P2

Сканер (`api-go/internal/reminders/scan.go`) сегодня идёт «по пользователям → их события».
Станет «по событиям → участники их календаря».

```
для каждого события в окне:
    участники = активные члены календаря события
    для каждого участника:
        offsets = event_reminder[event, участник] ?? пресет из его настроек
        для каждого offset: запланировать строку reminder(user_id = участник, ...)
```

Что при этом **не меняется и не должно**:

- Дедуп-индекс `idx_reminder_dedupe` уже включает `user_id`, поэтому две строки для двух
  участников не конфликтуют. Проверить это тестом, а не рассуждением.
- Sentinel'ы `-1` (snooze) и `-2` (дайджест) остаются.
- Пропуск пользователей без `tg_id` остаётся: у одного участника может не быть Telegram.
- Ретрай (`attempts`, миграция `000011`) работает как есть — он на уровне строки доставки.

⚠️ **Дайджест становится неоднозначным.** Сегодня он собирается по событиям пользователя.
После P3 «события пользователя» = события всех его календарей, включая общие. Это и есть
желаемое поведение, но текст дайджеста должен отличать общее от личного — иначе непонятно,
почему в сводке чужая встреча.

🔴 Это самая опасная часть работы: доставка уведомлений сейчас **работает и проверена живой
отправкой**. Переписывание скана обязано идти под тестами, которые есть, и e2e-проверкой на
staging до мержа.

## 7. Миграция существующих данных

Одной миграцией, без ручных действий:

1. Каждому пользователю создаётся личный календарь: `kind='personal'`, имя «Мой календарь»,
   `owner_id` = он, и строка `calendar_member(role='owner', status='active')`.
2. Все его события и задачи получают `calendar_id` этого календаря.
3. `event.reminder_offsets`, где массив непустой, копируется в
   `event_reminder(event_id, event.user_id, offsets)`. То же для задач.
4. `calendar_id` становится `NOT NULL`.

Откат (`.down.sql`) снимает `NOT NULL`, удаляет новые таблицы и колонки. Данные о смещениях при
откате не теряются, потому что старые колонки не удалялись (§4.3).

## 8. API

```
GET    /api/calendars                     список моих календарей + роль в каждом
POST   /api/calendars                     создать общий календарь
PATCH  /api/calendars/:id                 имя, цвет (owner)
DELETE /api/calendars/:id                 только пустой (см. §5.1)

POST   /api/calendars/:id/invites         пригласить по email или telegram username
POST   /api/calendars/invites/:token      принять приглашение
DELETE /api/calendars/:id/members/:userId исключить (owner) или выйти самому

PUT    /api/events/:id/reminders          мои смещения для этого события
PUT    /api/tasks/:id/reminders           то же для задачи
```

Существующие `GET /api/events`, `POST /api/events` и прочие **сохраняют форму**, но:

- `GET` возвращает события всех доступных календарей; у каждого события появляется
  `calendar_id` и признак `is_shared`.
- `POST` принимает необязательный `calendar_id`; без него — личный календарь создателя.

### 8.1. Приглашение

Создаётся `calendar_member` со `status='invited'` — **до принятия он не видит ничего**: helper
из §3 отдаёт только календари со `status='active'`.

Принять можно в вебе или прямо в боте кнопкой — инфраструктура кнопок появилась в P2 шаг 7
(`/api/svc/notifications/action`), и приглашение переиспользует её.

Приглашение несуществующего пользователя в v1 отклоняется с понятной ошибкой: регистрация по
приглашению — отдельная работа.

#### Кого именно приглашаем — проверено по схеме, а не предположено

| Поле | Что на самом деле |
|---|---|
| `email` | `TEXT UNIQUE`, **nullable** — резолвится однозначно, но у telegram-only пользователя его нет |
| `tg_username` | `TEXT`, **без уникальности**, nullable, и человек может сменить его в Telegram в любой момент |

Отсюда правила:

- Приглашение **по email** — основной путь: уникальность гарантирует схема.
- Приглашение **по tg_username** — поиск без учёта регистра; **0 или больше одного совпадения
  → отказ** с явной ошибкой, а не «взять первого». Совпадение по неуникальному полю — это то,
  как приглашение уезжает постороннему.

🔴 **Это упирается в известный дефект раздвоения личности.** В проде Денис существует **двумя**
записями: одна с `tg_id` и без email, другая с email и без `tg_id` — вход через Telegram-виджет
создаёт новую запись вместо привязки к существующей. Пока это не починено:

- приглашение делится с **той записью**, которую нашли, а не с человеком;
- у telegram-only участника нет email, значит пригласить его можно только по username, то есть
  по неуникальному полю.

**Слияние личностей — предусловие P3, а не его часть.** Строить приглашения поверх схемы, в
которой один человек = две записи, значит закладывать ошибку в фундамент.

## 9. Тестирование

| Слой | Что проверяем |
|---|---|
| Unit, Go | `CalendarIDsFor`: приглашённый (`invited`) не получает доступ; исключённый теряет; личный виден только владельцу |
| Unit, Go | Разрешение смещений: своя строка → она; нет строки → пресет; `[]` → тишина, а не пресет |
| Unit, Go | Сканер: одно общее событие с двумя участниками даёт **две** строки `reminder` с разными `user_id` и разными временами |
| Архитектурный тест | Ни один handler событий/задач не строит SQL по `user_id` напрямую — только через helper |
| e2e | Полный путь: создал общий календарь → пригласил → принял → завёл событие → **оба** видят → второй подвинул → у первого сдвинулось |
| e2e | Личное не протекает: событие в личном календаре не видно второму ни в списке, ни по прямому GET по id |
| Вручную на staging | Приходят **два** уведомления с разными смещениями — это то, что нельзя доказать юнит-тестом |

🔴 «Личное не протекает» — обязательный тест, а не желательный. Это единственный дефект в P3,
который нельзя откатить: чужие данные, один раз показанные, показаны.

## 10. Порядок реализации

Вертикальными срезами, каждый проверяем целиком:

0. 🔴 **Предусловие: слияние раздвоенных личностей** (§8.1). Не часть P3, но без него
   приглашение работает поверх схемы, где один человек — две записи. Отдельное решение Дениса,
   потому что это операция над продовыми данными.
1. Миграция + `CalendarIDsFor` + архитектурный тест. Поведение снаружи не меняется: у всех по
   личному календарю, всё работает как раньше. **Это самостоятельный, безопасный релиз.**
2. `GET/POST/PATCH/DELETE /api/calendars` + список календарей в UI, пока без приглашений.
3. Приглашение и принятие (веб), `status='invited'` → `active`.
4. Создание события и задачи в общем календаре, отображение `is_shared` в календаре.
5. Персональные напоминания: таблицы, ручки, переписанный сканер, тесты §9.
6. Принятие приглашения кнопкой в боте.

Шаг 1 стоит выпустить и пожить на нём: он трогает те самые 40 запросов, и любая ошибка в нём
проявится как «пропали события», что видно сразу.

## 11. Открытые вопросы

1. **Что показывать в дайджесте для общих событий** — помечать «общее», указывать второго
   участника, или ничего не менять? Решить до шага 5.
2. **Повторяющееся общее событие**: сейчас исключения повторов (`event_exception`) привязаны к
   событию. Если она удалит одно вхождение общей серии — оно исчезнет у обоих. Это ожидаемо,
   но стоит подтвердить, что ожидаемо.
3. **Часовые пояса**: у двоих могут быть разные. Событие хранится в UTC, показывается в зоне
   смотрящего — это уже так работает. Проверить на паре с разными зонами.
