## 1. Модель повторяющейся задачи

### Решение: `task.rrule` + разреженная таблица вхождений

🔴 **Это решение, а не данность — Денис оставил вопрос открытым** («again, not sure, ready to
discuss»), и отвергать его надо на ревью спеки, а не в коде.

```sql
ALTER TABLE task ADD COLUMN rrule TEXT;
ALTER TABLE task ADD COLUMN repeat_anchor DATE;      -- первое вхождение
ALTER TABLE task ADD COLUMN nag_minutes INTEGER;     -- §3

CREATE TABLE task_occurrence (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       UUID NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    task_id       UUID NOT NULL REFERENCES task(id)  ON DELETE CASCADE,
    occurrence    DATE NOT NULL,                     -- см. §1.2 про зону
    state         TEXT NOT NULL,                     -- done | skipped
    acted_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (task_id, occurrence)
);
```

**Почему так.** Это ровно форма `event_exception` (`000001_baseline:138`) — одна строка серии
плюс редкие записи о том, что с конкретным днём случилось. Год ежедневных таблеток — не 365
строк, а столько, сколько раз ты нажал кнопку. «Не одна задача и не разные» — буквально это.
Считать легко: `count(*) WHERE state='done'` за период.

**Альтернатива, которую Денис тоже назвал** — шаблон, порождающий настоящие строки-задачи.
Даёт полноценные подзадачи и произвольное редактирование одного дня, стоит генератора,
сканера по каждой строке и роста таблицы. Отвергнута как несоразмерная; вернуться, если
понадобится редактировать отдельное вхождение (переименовать «таблетки» только на вторник).

### 1.1 🔴 Состояние вхождения НЕ живёт в `task.status`

Отметить сегодняшние таблетки нельзя записью `status = 'DONE'` — серия исчезнет из всех
списков навсегда. Значит `status` у повторяющейся задачи означает **состояние серии**
(`TODO` — идёт, `DONE` — выключена насовсем), а «сделано сегодня» — строка в `task_occurrence`.

🔴 **И это меняет каждого читателя, который фильтрует `status = 'TODO'`.** Настоящая цена
фичи — здесь, а не в миграции. Полный список читателей на 18.09:

| Где | Файл | Что должен делать |
|---|---|---|
| Список задач | `api-go/internal/tasks/handlers.go:388,516` | у повторяющейся — считать состояние сегодняшнего вхождения |
| Сканер напоминаний | `api-go/internal/reminders/scan.go:209,371` | материализовать вхождения по `rrule`, а не по `due_date` |
| Планирование | `api-go/internal/planning/handlers.go:141` | повторяющаяся задача занимает слот один раз на дату |
| Экспорт | `api-go/internal/export/queries.go:63` | выгружать `rrule` и вхождения, иначе бэкап неполон |
| Счётчики календаря | `api-go/internal/calendars/crud.go:211,229` | серия — одна строка, не N |
| Веб | `web/src/pages/Tasks`, `Planning`, `Home/Dashboard`, `Tools/Kanban`, `Tools/Eisenhower` | те же правила, плюс свёрнутая строка «✅ сегодня» |
| Бот | `bot/internal/handlers/tasklist.go`, `today.go` | то же |

⚠ Архитектурный тест: запрос к `task` с фильтром по `status` **без** учёта `rrule` — это
дефект. Тест перечисляет файлы-читатели и краснеет, когда появляется новый.

### 1.2 🔴 Якорь вхождения — в зоне пользователя, не сервера

`occurrence` — `DATE`, и «19.09» должно значить 19.09 **у владельца задачи**. Сервер живёт в
UTC: без явного приведения к `user.timezone` отметка «сделал» после 21:00 по Москве попадёт на
следующий день.

Именно на этом я ошибся 17.09, прочитав `due_date` через `to_char` в сессии UTC и объявив
сдвиг на день там, где его не было (`learning-my-own-query-lied-twice-in-one-night`). Один
тест: пользователь в `Asia/Tokyo` отмечает вхождение в 23:00 местного — строка получает
сегодняшнюю местную дату.

### 1.3 Откладывание

- Кнопки: **день · 2 дня · 3 дня · неделя · месяц · свой срок**.
- «Отложить на N» = записать `state='skipped'` **на каждое вхождение, попавшее в окно**.
  Ритм серии не меняется (решение Дениса).
- Для недельной задачи «отложить на неделю» закрывает ровно одно вхождение — это то же
  правило, а не особый случай.

### 1.4 🔴 Грамматика RRULE у задач — та же, что у событий, и это ловушка

`api-go/internal/events/recurrence.go` `parseRRule` понимает только
`FREQ=DAILY|WEEKLY|MONTHLY` + `INTERVAL/COUNT/UNTIL`. Незнакомый ключ → ошибка разбора →
сущность показывается один раз и молча не повторяется. Ровно этот дефект уже ловили на
событиях (`FREQ=YEARLY`, `BYDAY=TU`), и закрыт он тестом
`TestEveryRuleTheBotWritesParsesInTheAPI`.

**Требование:** задачи используют **тот же** `parseRRule`, и тест зеркалится на задачи. Иначе
«каждый год пройти диспансеризацию» тихо не повторится, и мы заново пройдём тот же путь.

Связанный пункт релиза: **API отвергает RRULE, который не разбирает** (пункт 13). Сегодня он
принимает и молчит; должен возвращать 400 с именем непонятого ключа.

## 2. Задача ↔ событие

### 2.1 Связь

```sql
ALTER TABLE task  ADD COLUMN event_id UUID REFERENCES event(id) ON DELETE SET NULL;
```

Одна колонка на стороне задачи. `ON DELETE SET NULL` — удалив событие, задачу не теряем.
Это же закрывает третье замечание приёмки 11.09: «задача и созданное из неё событие не связаны».

### 2.2 Экран превращения

```
📝 → 📅 Сделать событием

Задача «Доделать сайт» станет событием:
Название  → Название          Доделать сайт
Срок 19.09 → Дата             19.09
—          → Время            ⚠ нужно указать
Теги      → Теги              нет
Календарь → Календарь         Личный

[🕐 Указать время]
[➡️ Перенести — задачи не останется]
[➕ Добавить событие и связать]
[✏️ Изменить поле] [⬅️ Отмена]
```

- 🔴 **Кнопка «Перенести» недоступна, пока есть хоть одно ⚠** — недостающее обязательное поле
  спрашивается до, а не после.
- **Перенести** — создать событие, перенести напоминания (`reminder.task_id → event_id`),
  удалить задачу. Одна транзакция.
- **Добавить и связать** — создать событие, записать `task.event_id`, задачу оставить.
  Карточка задачи после этого пишет «📅 Запланирована на 19.09 15:00».
- Обратное направление (событие → задача) — то же самое зеркально; недостающих обязательных
  полей у задачи нет, поэтому ⚠ там не бывает.

## 3. Частота напоминаний — и у задач, и у событий

### 3.1 🔴 Ловушка: ключ дедупликации напоминаний не содержит времени

`000015_reminder_calendar.up.sql:34`:

```
UNIQUE ON reminder (user_id, source_kind, COALESCE(event_id, task_id),
                    calendar_id, occurrence_start, minutes_before)
```

Долбёжка в 09:00 / 09:10 / 09:20 по одному вхождению — это строки, отличающиеся **только
`remind_at`**, которого в ключе нет. Второй INSERT конфликтует, и повторное напоминание тихо
не создаётся. Без решения в спеке это найдут только руками.

**Решение: перенос, а не новая строка.** Долбёжка не создаёт строк вперёд. Когда напоминание
доставлено и **не получило ответа**, сканер переносит ту же строку: `remind_at += nag_minutes`,
`status = 'PENDING'`. Ключ не трогается вовсе, новых колонок в индексе не нужно.

- Ответ (`done` / `ack` / `snooze` / отметка вхождения) останавливает перенос.
- Потолок: **не больше 6 переносов подряд** и не дольше конца дня вхождения. Бот, который
  долбит вторые сутки, будет отключён человеком целиком.
- ⚠ Sentinel-пространство `minutes_before` (`-1` snooze, `-2` дайджест, gotcha 12) при этом
  не расширяется — это сознательно: третий sentinel сделал бы колонку языком, а не числом.

### 3.2 Где хранится

`nag_minutes` — **на источнике** (`task.nag_minutes`, `event.nag_minutes`), не на строке
напоминания: это свойство вещи, о которой напоминают, и сканер читает его там же, где
`reminder_offsets`. По умолчанию `NULL` = не долбить. В карточке — строка «🔂 Повторять
напоминание: нет».
