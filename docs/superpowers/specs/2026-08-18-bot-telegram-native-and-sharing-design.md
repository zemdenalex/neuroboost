# Бот: современная библиотека, шаринг из чата и списки-чеклисты

**Статус:** черновик на ревью Дениса · **Дата:** 2026-08-18
**Разбор с доказательствами:** `docs/razbor-bot-telegram-native-2026-08-18.md`

## Откуда взялась эта спека

Денис прошёл dev-бота руками 19.08 и сказал дословно: *«notes are tasks for some reason,
tasks creation is bad, calendar view is much worse than what it was in previous versions,
settings don't work, menu doesn't show extra buttons, only reffer to keyboard buttons»*.
Затем, увидев разбор: *«I think we should add some interactions with new telegram bot
features… I want quick tasklist creation and sharing tasks or events between users with
telegram linked to their neuroboost, or even calendars»*.

Работа разложилась на пять кусков; **эта спека берёт три из них**, потому что остальные два
ни от чего не зависят и делаются отдельно:

| # | Кусок | Здесь? |
|---|---|---|
| 1 | Навигация inline-first + три регрессии календаря | ❌ своя спека |
| 2 | Заметки как отдельная сущность (`/api/notes` + миграция) | ❌ своя спека |
| 3 | Создание задачи: строка + мастер «Подробнее» | ❌ своя спека |
| 4 | **Библиотека, шаринг, списки** | 🟢 **эта** |
| 5 | Mini App — календарь внутри Telegram | ❌ своя спека, после этой |

Порядок выбран Денисом: *«сначала спека на телеграм-нативное и шаринг»*.

## Цель

Бот получает библиотеку, на которой можно строить дальше; из чата можно позвать человека
в общий календарь; список дел живёт одним сообщением с галочками.

## Границы — что НЕ входит

- ❌ **Нативные чеклисты Telegram** (`sendChecklist`). Решение Дениса 18.08 — заменить своим
  списком на inline-кнопках. Основание: метод работает на имя **Telegram Business**-аккаунта,
  а Business требует Premium у владельца, то есть возможность была бы у него и не была бы у
  того, с кем он делится. Разбор §7.
  ⚠ **Граница этой проверки, чтобы решение принималось с открытыми глазами:** ограничение
  выведено из трёх независимых описаний метода, а **не** прочитано в таблице параметров —
  страница `core.telegram.org/bots/api` обрезается при выборке, а машиночитаемые мирроры
  стоят на Bot API 8.3, где чеклистов ещё нет. Закрывается одним живым вызовом после среза 0.
  Если он покажет, что `business_connection_id` необязателен, решение можно пересмотреть.
- ❌ **Mini App**, `savePreparedInlineMessage`, rich messages, topics, ephemeral. Названы в
  разборе §2 как доступные после миграции — но не в этой спеке.
- ❌ **Правка навигации, заметок, создания задачи** — кроме мест, которых миграция касается
  механически.
- ❌ **Прод-релиз бота** без отдельного «да» Дениса.
- ❌ **Веб** не трогаем.

## Глобальные ограничения

Действуют на каждую задачу каждого плана из этой спеки.

- Модулей **два** и они не пересекаются: `cd api-go && go build ./... && go vet ./... && go test ./...`
  **и то же самое** в `cd bot`. Сборка в одном не заходит в другой.
- 🔴 **`callback_data` — 64 байта.** UUID занимает 36. Каждая новая клавиатура получает тест,
  утверждающий длину, а не арифметику в комментарии.
- 🔴 **Никакого секрета в логах.** Всё, что печатается или уезжает в другой процесс, проходит
  через `logsafe.Redact` / `deliveryReason`. Редакция — там, где секрет рождается, не там, где
  печатается (gotcha 14).
- 🔴 **Всякая фоновая горутина имеет `recover`** (gotcha 9).
- 🔴 **Утверждение о v0.2.1 цитирует строку `bot.action` в `_legacy/…/v0.2.1/apps/bot/src/index.mjs`**,
  никогда не клавиатуру в `keyboards.mjs`. Клавиатура соврала дважды за две ночи.
- 🔴 **Тест засчитывается, только если показано, что он краснеет.** Ломаем охраняемое,
  смотрим на красное, чиним. Зелёный тест без этого — не свидетельство.
- Существующие миграции не правим — только новые. Следующая свободная — **000017**.
- Запросы pgx только параметризованные.
- `git add` конкретных файлов. Со-автор Claude/Anthropic — никогда.

# Срез 0 — миграция на `go-telegram/bot`

## Зачем

`bot/go.mod` держит `go-telegram-bot-api/v5 v5.5.1` — Bot API ~6.1, лето 2022. Проверено с
положительным контролем: `InlineKeyboardButton` в библиотеке есть, `WebAppInfo`,
`KeyboardButtonRequestUsers`, `UsersShared` — нет (разбор §1).

`MakeRequest` позволяет **отправить** новый метод, но `GetUpdatesChan` отдаёт уже разобранные
`Update`, где новых полей нет и заглушки под сырой JSON тоже нет. **Входящей половины у лазейки
не существует**, а выбор контакта — это именно входящее (`message.users_shared`).

## Выбор

`github.com/go-telegram/bot@v1.23.0`. Bot API 10.2 (14.07.2026). В `go.mod` библиотеки **нет
блока `require` вовсе** — зависимостей ноль, что отдельно важно для хоста, куда бота носят руками.

Отвергнуты: `mymmrac/telego` (тянет `fasthttp` и `go-json` в транспорт), `tucnak/telebot`
(намеренно не 1:1 с API — для нативных новинок это минус).

## Форма

Библиотека меняет модель: вместо `for update := range updates` — регистрация обработчиков и
`context.Context` первым аргументом каждого метода.

```go
// bot/cmd/main.go
b, err := bot.New(cfg.TelegramToken,
    bot.WithDefaultHandler(h.HandleUpdate),
)
b.Start(ctx)
```

🔴 **Границы миграции — только транспорт.** Продуктовая логика (`internal/api`, `internal/parse`,
`internal/state`, `internal/format`, `internal/auth`, `internal/logsafe`) остаётся как есть.
Меняются: `cmd/main.go`, `internal/handlers/*`, `internal/keyboards/*`, `internal/notifier/*` —
и только в тех строках, где упоминается тип библиотеки.

**Соответствие типов:**

| `tgbotapi` (v5.5.1) | `go-telegram/bot` (v1.23.0) |
|---|---|
| `tgbotapi.NewMessage(chatID, text)` + `bot.Send` | `b.SendMessage(ctx, &bot.SendMessageParams{ChatID, Text})` |
| `tgbotapi.NewEditMessageTextAndMarkup(...)` | `b.EditMessageText(ctx, &bot.EditMessageTextParams{ChatID, MessageID, Text, ReplyMarkup})` |
| `tgbotapi.NewCallback(cb.ID, "")` | `b.AnswerCallbackQuery(ctx, &bot.AnswerCallbackQueryParams{CallbackQueryID})` |
| `tgbotapi.InlineKeyboardMarkup` | `models.InlineKeyboardMarkup` |
| `tgbotapi.ReplyKeyboardMarkup` | `models.ReplyKeyboardMarkup` |
| `msg.ParseMode = "HTML"` | `ParseMode: models.ParseModeHTML` |
| `cb.Message` (может быть nil) | `update.CallbackQuery.Message` — **та же нулевая проверка обязана уцелеть** |

## Что обязано уцелеть при миграции — и это главное в этом срезе

Каждый пункт ниже — починка, стоившая отдельного разбора. Миграция транспорта — ровно та
операция, в которой такое теряется молча.

| Свойство | Где сейчас | Почему нельзя потерять |
|---|---|---|
| `cb.Message == nil` не роняет процесс | `handler.go`, `HandleCallback` | Нажатие под старым напоминанием клало **весь** бот, у всех |
| Callback всегда отвечен | там же | Иначе спиннер крутится вечно и бот читается как зависший |
| Ошибка отправки попадает в лог | `handler.go`, `send` | Молчание в чате И в логе не диагностируется потом |
| `"message is not modified"` не шумит | `handler.go`, `editHTMLWithKeyboard` | Двойной тап по той же странице — не ошибка |
| Токен не течёт в лог | `logsafe.Redact` во всех обработчиках ошибок | gotcha 14, стоило ротации |
| `ensureAuth` до всякого обработчика | `handler.go`, `ensureAuth` | Без него бот ходит в API без заголовка |
| Кнопки напоминания идут **до** `ensureAuth` | `HandleCallback` | Они на сервисном токене; отказ логина не должен мешать snooze |

## 🔴 Ловушка, которой в старой библиотеке не было: `WithWorkers`

`state.Store` раздаёт **указатель** на `UserState`, и обработчики пишут `CurrentFlow`,
`FlowStep`, `FlowData` через него **без блокировки**. Мьютекс защищает карту, а не структуры
в ней. Сегодня это безопасно ровно по одной причине — **писатель один**, и это записано
комментарием в `internal/state/state.go`.

Новая библиотека держит пул воркеров. Проверено: `defaultWorkers = 1` (`bot.go:20`), то есть
по умолчанию единственный писатель сохраняется и допущение уцелеет.

🔴 **Но `bot.WithWorkers(n)` при `n > 1` ломает его молча** — гонка на карте `FlowData`
не даёт ошибки, она даёт мусор у случайного пользователя раз в неделю.

**Правило для этого среза:** `WithWorkers` не передавать. Если когда-нибудь понадобится —
сперва сделать `state.Store` потокобезопасным по-настоящему (методы вместо выданного
указателя), и доказать это `go test -race`, а не рассуждением.

**Проверка среза 0 — три уровня, и первые два недостаточны:**

1. `cd bot && go build ./... && go vet ./... && go test ./...` — зелено.
2. Тест на каждую строку таблицы выше, каждый показан красным до починки.
3. 🔴 **Ручной проход dev-бота по `docs/proverka-bota-2026-08-19.md`** после выкатки на nl-2.
   Зелёные тесты и выкаченный бот — разные утверждения (gotcha 19).

# Срез 1 — позвать человека в общий календарь прямо из чата

## Что уже есть на сервере

P3 выкачен. Живые роуты (`api-go/cmd/api/main.go:177–191`): создание календаря, участники,
роли, приглашение по email, ссылка-приглашение с токеном, принятие/отклонение, удаление
участника. **Задачи наследуют шаринг бесплатно** — у задачи есть `calendar_id`.

🔴 **Единственная дыра:** `inviteRequest` — это `{Email string, Role string}`
(`members_handlers.go:13`). Пути «пригласить по Telegram-id» нет.

## Два канала, оба в одном срезе (решение Дениса)

### Канал A — ссылка. Правок API не требует вовсе.

`POST /api/calendars/{id}/invite-links` уже отдаёт токен. Бот делает ссылку и кладёт её
кнопкой `copy_text`, чтобы копировалась одним тапом. Пересылается кому угодно, в том числе
человеку без Telegram.

### Канал B — выбор контакта. Требует нового пути в API.

🔴 **Деталь, определяющая форму экрана:** `KeyboardButtonRequestUsers` — кнопка **reply**-клавиатуры,
не inline. Значит экран «Поделиться» показывает одноразовую reply-клавиатуру поверх обычной,
а не inline-кнопку. Это не обходится.

```go
// bot/internal/keyboards/share.go
models.KeyboardButton{
    Text: "👤 Выбрать контакт",
    RequestUsers: &models.KeyboardButtonRequestUsers{
        RequestID:       int32(requestID),
        UserIsBot:       false,
        MaxQuantity:     1,
        RequestName:     true,
        RequestUsername: true,
    },
}
```

Ответ приходит как `update.Message.UsersShared` → `models.UsersShared{RequestID int, Users []SharedUser}`,
где `SharedUser.UserID int64` — это Telegram-id.

### Новый путь в API

`POST /api/calendars/{id}/invites-by-telegram`, тело `{"tg_id": 123456789, "role": "editor"}`.

Реализация — **близнец `InviteByEmail`** (`api-go/internal/calendars/members.go:154`),
отличается одной строкой поиска:

```go
// InviteByTelegramID mirrors InviteByEmail; only the lookup differs.
//
// tg_id is UNIQUE in the schema (000001_baseline.up.sql:33), so at most one row
// matches — the same guarantee email has, and the reason neither needs a LIMIT.
err := db.Pool.QueryRow(ctx,
    `SELECT id::text FROM "user" WHERE tg_id = $1`, tgID).Scan(&inviteeID)
if errors.Is(err, pgx.ErrNoRows) {
    return Member{}, ErrInviteeNotFound   // "у этого человека нет NeuroBoost"
}
```

🔴 **`ON CONFLICT DO NOTHING`, а не `DO UPDATE`** — ровно как в `InviteByEmail`, и по той же
причине: существующая строка может быть ACTIVE-членством, и перезапись понизила бы активного
участника до «приглашён», отрезав ему доступ, кнопкой с надписью «пригласить».

### Состояние между «нажал Поделиться» и «выбрал контакта»

Между двумя событиями надо помнить, **в какой календарь** зовём. `request_id` — int32, в него
UUID не влезает. Держим намерение в `state.Store` по chatID.

⚠ **Названное ограничение:** бот выкатывается руками и перезапуск обнуляет `state.Store`. Если
перезапуск случится между двумя тапами, `users_shared` придёт без намерения — тогда бот честно
говорит «не помню, для какого календаря; нажми Поделиться ещё раз», а **не** угадывает календарь.
Молча выбрать «первый попавшийся» — это записать человека не туда.

─────────────────────────────

[ 🔗 Ссылка-приглашение        ]
[ 👤 Выбрать контакт           ]

# Срез 2 — список с галочками, одним сообщением

Нативный чеклист отвергнут (см. Границы). Строим свой: **одно сообщение, кнопки-галочки,
правка на месте**.

## Данные: новой сущности не требуется

У задачи уже есть `parent_id` (`api-go/internal/tasks/types.go`, принимается в
`CreateTaskRequest` и пишется в `handlers.go:480`). Значит:

- **Список = родительская задача.** Пункты — её дети.
- **«Задачи на сегодня» = запрос**, а не сущность: те же кнопки поверх результата выборки.

🟢 **Миграции не нужно ни одной.** Это и есть причина выбрать `parent_id` вместо новой таблицы.

## Четыре формы, которые заказал Денис

| Форма | Как устроена |
|---|---|
| Список строкой → чеклист + задачи | `хлеб, молоко, аптека` → **два запроса**: `POST /api/tasks` создаёт родителя, затем `POST /api/tasks/batch` создаёт детей с его `parent_id`. Одним batch'ом нельзя — детям нужен id, которого до первого ответа не существует |
| Галочка → задача DONE | Нажатие шлёт `PATCH /api/tasks/{id}` со `status`, потом перерисовывает сообщение |
| «Задачи на сегодня» чеклистом | Те же кнопки поверх выборки дня |
| Общий список на двоих | Родитель создан в общем календаре → оба видят, оба отмечают |

## Callback: как влезть в 64 байта

Наивное «нести и список, и пункт» не влезает: два UUID это 78 байт. Поэтому **callback несёт
только id задачи, а способ перерисовки — в префиксе**:

| Префикс | Длина | Что делает |
|---|---|---|
| `ckp_<taskID>` | 4 + 36 = **40** ✓ | Пункт списка-родителя: переключить, затем GET задачи → взять `parent_id` → перерисовать по детям |
| `ckd_<taskID>` | 4 + 36 = **40** ✓ | Пункт дневного списка: переключить, затем перерисовать выборкой дня |

🔴 **Почему не состояние в сессии:** бот выкатывается руками, перезапуск обнуляет `state.Store`,
а сообщение со списком остаётся в чате навсегда. Кнопка, работающая только до перезапуска, —
это кнопка, которая однажды перестанет работать без всякого признака. Callback самодостаточен,
и потому идемпотентен и переживает рестарт. Тот же довод, что у `TaskScheduleWhen`.

## Вид

```
🧾 Покупки · 1 из 3
─────────────────────────────
[ ☑ хлеб                     ]
[ ☐ молоко                   ]
[ ☐ аптека                   ]
[ ➕ Добавить ][ « Назад      ]
```

## ⚠ Ограничение, которое обязано быть названо вслух

Общий список живёт **отдельным сообщением в каждом чате**. Когда второй человек ставит
галочку, сообщение первого **не обновляется само** — Telegram не даёт боту список сообщений,
которые он когда-то отправил. Первый увидит правду, когда откроет список заново.

Не лечим в этом срезе. Лечится либо запоминанием message_id на каждого участника, либо
Mini App — и то и другое дороже, чем сам срез.

# Ошибки

| Что произошло | Что видит человек |
|---|---|
| API недоступен | «⚠️ Не дозвонился до сервера. Попробуй через минуту.» — без деталей транспорта: там URL с токеном |
| Приглашаемого нет в NeuroBoost | «У этого человека ещё нет NeuroBoost. Отправь ему ссылку-приглашение.» + кнопка на канал A |
| Человек уже участник | «Он уже здесь» — не ошибка, и не понижаем его роль |
| Намерение потеряно рестартом | «Не помню, для какого календаря. Нажми «Поделиться» ещё раз.» |
| Задача из списка удалена в вебе | Перерисовка её просто не покажет; список остаётся рабочим |
| Родитель создан, а batch с детьми упал | 🔴 Остаётся пустой список — видимый мусор. Бот удаляет родителя и говорит «не сохранилось, попробуй ещё». Половина операции хуже, чем ни одной: пустой список выглядит как рабочий |
| Telegram отверг правку («not modified») | Молчим — двойной тап не ошибка |

# Тестирование

**Go, оба модуля.** На каждый срез:

- Срез 0: тест на каждую строку таблицы «что обязано уцелеть», **каждый показан красным**
  до починки. Плюс тест длины `callback_data` на все клавиатуры.
- Срез 1: `InviteByTelegramID` против настоящей базы — с проверкой, что подмена `tg_id` на
  несуществующий даёт `ErrInviteeNotFound`, а повтор даёт `ErrAlreadyMember` и **не** меняет
  роль активного участника. 🔴 Тест на разбор JSON здесь ничего не доказал бы: путь падает в
  базе, а не в декодере.
- Срез 2: `buildChecklist` (чистая функция: задачи → текст + клавиатура) — счётчик «1 из 3»,
  пустой список, список из 30 пунктов, заголовок длиннее лимита, **рунный** обрез (заголовки
  русские, байтовый обрез покажет `�`).

**e2e Playwright** этот срез не покрывает: бот не в браузере. Ручной проход — часть приёмки,
не приписка.

# Порядок и что каждый срез даёт сам по себе

| Срез | Даёт сам по себе | Зависит от |
|---|---|---|
| **0** Библиотека | Ничего видимого. Бот работает ровно как раньше — это и есть критерий | — |
| **1** Шаринг | Позвать человека в календарь из чата, двумя способами | **0** — `UsersShared` в старой библиотеке не существует |
| **2** Списки | Список дел одним сообщением с галочками | 🟢 **ни от чего.** Inline-кнопки, `PATCH /api/tasks/{id}`, `parent_id` и `/api/tasks/batch` работают на `v5.5.1` уже сегодня |

🔴 **Отсюда следует порядок, и он не 0 → 1 → 2.** Срез 0 по определению не даёт ничего
видимого, срез 1 без него не начать — значит при порядке 0 → 1 → 2 Денис не видит **ничего
нажимаемого** всё время, пока идёт миграция, а миграция транспорта — самое вероятное место
неприятных сюрпризов в этой спеке.

**Срез 2 идёт первым.** Он единственный здесь, который можно потрогать, и он ничего не ждёт.
Затем 0, затем 1.
