# P2 — Уведомления и бот

> **Статус:** design, ожидает review Дениса · **Дата:** 2026-07-27 · **Ветка:** `develop`
> **Место в очереди:** ~~P1 (готово)~~ → **P2 (этот документ)** → P3 shared events

## 1. Задача

Дословно: *«я не получаю уведомлений, поэтому мне приходится смотреть их вручную»*. Приложение
знает, что и когда происходит, но молчит. Пока оно молчит, календарь бесполезен как календарь.

**Целевой сценарий:** событию нужно пять напоминаний — за месяц, неделю, 3 дня, день и час.
Все пять приходят. Другому нужно одно за 5 минут — приходит одно. Без настройки «умности»,
без обучения. Просто работает.

## 2. Что НЕ входит

- Обучение / adaptive timing / «умные» подсказки когда напомнить
- Уведомления кому-то кроме себя (это P3)
- Email, push в браузер, SMS — **только Telegram** в этой итерации
- Богатый бот-ассистент. Обычный бот доводится до рабочего состояния, но не расширяется.

## 3. Главное архитектурное следствие

**Отправка в Telegram обязана уехать с RU-хоста.** `bot/cmd/main.go` уже умеет
`TELEGRAM_PROXY`, потому что RU-хостинг блокирует Telegram, и ROADMAP помечает v0.4.6 как
«bot blocked by proxy». Идеальный планировщик доставит ноль сообщений, если исходящий трафик
до `api.telegram.org` не проходит.

В Nivium эта же проблема решена **без прокси**: `bot-tg` крутится контейнером на зарубежном
panel-хосте (`deploy.sh` → `root@213.170.133.242`), Telegram Stars и все команды работают.
Берём ровно этот путь.

Отсюда — разделение ответственности:

```
   RU-хост (наш API + БД)                     Зарубежный хост
┌──────────────────────────────┐          ┌──────────────────────────┐
│ api-go                       │          │ neuroboost-notifier      │
│  · знает расписание          │  HTTPS   │  · только доставка       │
│  · раскрывает RRULE          │◄─────────┤  · шлёт в Telegram       │
│  · решает, что пора слать    │  \_ pull │  · принимает callback'и  │
│  · пишет журнал доставки     │          │                          │
└──────────────────────────────┘          └──────────────────────────┘
```

Вся логика остаётся там, где уже живут `expandRecurrence` и БД. За границу уезжает **только
egress**. Ни бизнес-логики, ни копии БД на зарубежном хосте — если он умрёт, ничего не теряется,
кроме доставки за это время.

## 4. Данные

### 4.1. Смещения хранятся на сущности, а не строками

Ты выбрал «считать на лету из RRULE». Значит, набор напоминаний — свойство события, а не
набор заранее сгенерированных строк:

```sql
ALTER TABLE event ADD COLUMN reminder_offsets INTEGER[] NOT NULL DEFAULT '{}';
ALTER TABLE task  ADD COLUMN reminder_offsets INTEGER[] NOT NULL DEFAULT '{}';
```

Значения — минуты до начала (события) или до `due_date` (задачи). `[43200, 10080, 4320, 1440, 60]`
— это ровно твои месяц / неделя / 3 дня / день / час.

Почему так, а не строки наперёд:
- Повторяющееся событие с пятью смещениями и ежедневным повтором — это **1825 строк в год**
  на одно событие. Здесь — одна колонка.
- Правка серии (сдвинул время, поменял RRULE) не требует перегенерации: следующий скан просто
  посчитает заново.
- `expandRecurrence` (`events/recurrence.go:81`) уже даёт вхождения в окне. Переиспользуем.

### 4.2. Таблица `reminder` становится журналом доставки

`reminder` существует в `000001_baseline` с первого дня и **не используется ни одной строкой Go**.
Перепрофилируем её в журнал отправленного — это то, что действительно нужно хранить, потому что
без него перезапуск воркера пришлёт всё повторно.

```sql
ALTER TABLE reminder ADD COLUMN source_kind TEXT;          -- 'EVENT' | 'TASK' | 'DIGEST'
ALTER TABLE reminder ADD COLUMN task_id UUID REFERENCES task(id) ON DELETE CASCADE;
ALTER TABLE reminder ADD COLUMN occurrence_start TIMESTAMPTZ;

-- Идемпотентность: одно вхождение × одно смещение = одна отправка. Навсегда.
CREATE UNIQUE INDEX idx_reminder_dedupe
  ON reminder (user_id, source_kind, COALESCE(event_id, task_id), occurrence_start, minutes_before)
  NULLS NOT DISTINCT;
```

`occurrence_start` — вот почему повторяющиеся события работают: ключ дедупликации содержит
**конкретное вхождение**, а не только id серии. Ежедневная встреча в 10:00 шлёт напоминание
каждый день и ни одного дважды.

🔴 **NULL в ключе не конфликтует — это ломало бы дедупликацию ровно там, где она нужна.**
В Postgres по умолчанию два NULL в уникальном индексе считаются разными значениями. У дайджеста
нет вхождения, у snooze нет `minutes_before` — то есть обе эти строки прошли бы уникальный
индекс сколько угодно раз. А окно скана 3 минуты при тике раз в минуту означает, что каждое
напоминание просматривается ~3 раза: дайджест уходил бы **трижды каждое утро**.

Поэтому — **два независимых предохранителя, оба обязательны**:

1. `NULLS NOT DISTINCT` в индексе (Postgres 15+; у нас `postgres:16-alpine`, доступно).
2. **Явные значения вместо NULL** в обоих случаях:
   - дайджест: `occurrence_start` = полночь местных суток пользователя, к которым он относится
   - snooze: `minutes_before = -1` (sentinel «разовое, смещения нет»)

Одного второго пункта было бы достаточно, но первый защищает от следующей строки с NULL,
которую кто-то добавит, не прочитав этот абзац.

⚠️ Существующие строки `reminder` в проде: их нет (таблица никогда не заполнялась), но миграция
всё равно обязана пережить непустую таблицу. Порядок строго такой:

1. `source_kind` добавляется **nullable** — иначе `ALTER` упал бы на непустой таблице;
2. бэкфилл `'EVENT'` там, где `event_id IS NOT NULL`, `'TASK'` где `task_id IS NOT NULL`;
3. `ALTER TABLE reminder ALTER COLUMN source_kind SET NOT NULL;`
4. и только теперь уникальный индекс.

🔴 **Шаг 3 обязателен, и его легко потерять.** Оставленный nullable `source_kind` вместе с
`NULLS NOT DISTINCT` превращает NULL в **полноценное значение ключа дедупликации**: строка с
`source_kind IS NULL` не конфликтует ни с `'EVENT'`, ни с `'TASK'` — то есть открывает ровно ту
дыру, которую весь предыдущий абзац закрывает.

Проверка схемы (`000001_baseline.up.sql:151-165`, сверено 2026-07-27): в таблице уже есть
`user_id`, `event_id`, `minutes_before`, `remind_at`, `status`, `channel`, `message`, `sent_at` —
все имена в этом разделе существуют, добавляем только `source_kind`, `task_id`,
`occurrence_start`. Postgres — `16-alpine`, `NULLS NOT DISTINCT` доступен (PG15+).

### 4.3. Пресеты

Хранятся в `"user".settings` JSONB — миграции не нужно (как в P1):

```json
{
  "reminders": {
    "presets": {
      "важное":  [43200, 10080, 4320, 1440, 60],
      "обычное": [1440, 60],
      "без":     []
    },
    "default_event_preset": "обычное",
    "default_task_preset": "обычное",
    "digest_at": "08:00",
    "digest_enabled": true,
    "quiet_hours_respected": true
  }
}
```

**Кто применяет пресет — бэкенд, при создании.** `CreateHandler` события и задачи, если
`reminder_offsets` в запросе не пришли **вообще** (не пришёл пустой массив — именно отсутствие
поля), подставляет смещения из `default_event_preset` / `default_task_preset`. Пустой массив в
запросе означает «намеренно без напоминаний» и не перезаписывается.

Почему бэкенд, а не фронт: иначе событие, созданное из бота или импорта, молча останется без
напоминаний, и настройка окажется свойством одной формы, а не пользователя.

`quiet_hours_start` / `quiet_hours_end` **уже есть** в `UserSettings` (`api/auth.ts:28-29`) и
сейчас ни на что не влияют. Здесь они наконец начинают работать: напоминание, попавшее в тихие
часы, сдвигается на конец тихого окна, а не теряется. Исключение — напоминания за ≤15 минут:
они бесполезны, если сдвинуты, поэтому в тихие часы просто не отправляются.

## 5. Воркер

Один тикер в `api-go`, раз в минуту (`internal/reminders/`):

1. Окно скана: `[now − 2 min, now + 1 min]` — перехлёст, чтобы пропуск тика (деплой, рестарт)
   не потерял напоминание. Дедупликация делает перехлёст безопасным.
2. Для каждого пользователя:
   - события с непустым `reminder_offsets`, у которых **вхождение** попадает в
     `[now + offset − окно]` — вхождения берутся из `expandRecurrence` с учётом `event_exception`
   - задачи с `due_date` и непустым `reminder_offsets`, **кроме** уже `DONE`/`CANCELLED`
   - дайджест, если местное время пользователя совпало с `digest_at`
3. `INSERT ... ON CONFLICT DO NOTHING` в `reminder` со статусом `PENDING`. Конфликт = уже
   отправляли, молча пропускаем.
4. Ничего не шлём сами. Отправка — дело нотифаера.

**Почему воркер, а не cron:** нужен доступ к `expandRecurrence` и пулу pgx, обе живут в процессе API.

### 5.1. Контракт с нотифаером

Две ручки, защищённые **service-токеном** (заголовок `X-Service-Token`), не пользовательским JWT —
нотифаеру нужны напоминания всех пользователей сразу:

```
GET  /api/svc/notifications/pending   → [{id, tg_id, text, buttons[], source_kind, source_id}]
POST /api/svc/notifications/{id}/ack  → {delivered: true} | {delivered: false, error: "..."}
```

🔴 **Это не internal-ручки, как бы их ни назвали.** Сейчас бот ходит в API по
`API_BASE=http://api:8080` внутри compose-сети. После переезда на зарубежный хост это станет
**публичный HTTPS-адрес**, и `pending`, отдающий `tg_id` и текст сообщений **всех**
пользователей, будет доступен из интернета, а единственной защитой останется статический токен.
Поэтому префикс `/api/svc/`, а не `/api/internal/` — чтобы никто не считал, что тут есть сетевая
изоляция. Обязательно:

- сравнение токена **constant-time** (`crypto/subtle.ConstantTimeCompare`), не `==`
- rate-limit на префикс `/api/svc/`
- отдельный лог-канал: любой запрос с неверным токеном пишется с IP

- `pending` возвращает максимум 100, только строки с `remind_at <= now()` (иначе snooze,
  у которого `remind_at` в будущем, уедет в момент создания), и помечает выданное `SENDING`
  с меткой времени; строка `SENDING` старше 5 минут снова становится `PENDING` (нотифаер упал
  между выдачей и ack).
- Пользователи без `tg_id` пропускаются на этапе скана — их напоминания не создаются вовсе,
  а не копятся неотправляемыми.
- Service-токен — переменная окружения на обеих сторонах. **В файлы не пишется** (правило
  проекта: креды только в Tracker App).

## 6. Кнопки в уведомлении

Ты выбрал кнопки. Минимальный набор, по одному ряду:

| Тип | Кнопки |
|-----|--------|
| Событие | `Понятно` · `Отложить 10 мин` |
| Задача | `Готово` · `Отложить на завтра` · `Открыть` |
| Дайджест | `Открыть календарь` |

Callback идёт в нотифаер → `POST /api/svc/notifications/action` с service-токеном и
`tg_id` → API находит пользователя по `tg_id` и выполняет действие. `Готово` ставит задаче
`DONE` — ровно тот путь, что и чекбокс из P1.

**«Отложить 10 мин»** создаёт разовую строку `reminder` с `minutes_before = NULL` и явным
`remind_at`. Колонка `remind_at` для этого уже есть в baseline.

## 7. Обычный бот

Доводим до рабочего состояния, не расширяем. Сейчас в `bot/` 903 строки: команды, календарь,
задачи, `today`, flows, клавиатуры. Что нужно:

- Проверить, что все команды живы после переезда на зарубежный хост
- `/start` с привязкой аккаунта через `POST /api/auth/telegram` (эндпоинт есть, `main.go:77`)
- Закрытие задачи из бота — тот же путь, что кнопка `Готово`

**Один процесс или два?** Один: нотифаер — это горутина внутри существующего бота, а не второй
контейнер. У них общий бот-токен и общий HTTP-клиент к Telegram; разделять — значит держать два
токена и два деплоя ради одного `for`-цикла.

## 9. Тестирование

Чистая логика — обязательно тестами:
- `dueReminders(event, offsets, window, now, tz)` — вхождения из RRULE × смещения → что пора
- дедупликация: повторный скан того же окна не создаёт вторую строку
- тихие часы: сдвиг на конец окна; напоминание ≤15 мин в тихие часы не шлётся
- дайджест: срабатывает один раз в местные сутки пользователя, не по UTC
- миграция: непустая `reminder` переживает добавление уникального индекса

Доставка — интеграционно, вручную на staging: один реальный бот, одно реальное сообщение.

## 10. Порядок реализации

1. Миграция `000010`: `reminder_offsets` на event и task, журнальные колонки + уникальный индекс
2. `dueReminders` — чистая функция + тесты (**до** любого воркера)
3. Тихие часы и дайджест — чистые функции + тесты
4. Воркер-тикер + скан + `ON CONFLICT DO NOTHING`
5. Внутренние ручки `pending` / `ack` + service-токен
6. Нотифаер-горутина в боте: pull → send → ack
7. Кнопки и callback'и
8. `<ReminderOffsets/>` в редакторе события
9. То же в задаче + секция Settings
10. Переезд бота на зарубежный хост, деплой, живая проверка

Пункты 1–6 = напоминания уже приходят. Дальше — управляемость.
