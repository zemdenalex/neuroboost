# P1 — Быстрое создание и ведение задач (quick capture)

> **Статус:** design, ожидает review Дениса · **Дата:** 2026-07-27 · **Ветка:** `develop` (после promotion v0.4.10)
> **Место в очереди:** promotion v0.4.10 → **P1 (этот документ)** → P2 notifications → P3 shared events

## 1. Задача

Сегодня, чтобы завести задачу, нужно: нажать «+», дождаться модалки, ввести название,
дотянуться до Save мышью, модалка закрывается, повторить. Пять действий и переключение
контекста на каждую задачу. При 50+ задачах в день это и есть та причина, по которой
приложением нельзя пользоваться.

**Целевой сценарий (дословно):** вечером, перед сном, открыть Tasks, набрать
`задача 1` → Enter → `задача 2` → Enter → `задача 3` → Enter → Esc. Ноль решений,
ноль мыши, ноль модалок.

**Успех измеряется одним числом:** действий на одну простую задачу = **1** (текст + Enter).

## 2. Что НЕ входит

Явно за границей этой спеки — чтобы не расползлось:

- Kanban, Eisenhower, smart suggestions, reflections, gamification
- Notifications / Telegram (это P2 — но чекбокс «done» в боте появится там)
- Shared / assigned задачи (это P3)
- Recurring для задач (у events есть, у tasks нет — отдельная работа, не здесь)
- Редизайн страницы Tasks целиком. Существующая группировка по priority остаётся.
- Drag-n-drop переупорядочивание задач

## 3. Ключевое решение: сущности не добавляем

Обсуждали `task_list` как отдельную сущность. **Отклонено.** Причина: у нас, в отличие от
Telegram, задачи существуют самостоятельно — «список» это просто задача с детьми. В схеме
уже есть всё нужное:

| Что нужно | Что уже есть в `000001_baseline` |
|---|---|
| Дерево задач | `task.parent_id UUID REFERENCES task(id)` + `idx_task_parent` |
| Группы / метки | `task.tags TEXT[]`, `task.contexts TEXT[]` |
| Оценка времени | `task.estimated_minutes INTEGER` |
| Факт времени | `task.actual_minutes` (migration `000009`) |
| Настройки пользователя | `"user".settings JSONB` (migration `000005`) |

**Следствие: P1 не требует ни одной миграции.** Это чисто frontend + один batch-эндпоинт.
Дерево задач даёт и «список дел» (родитель + дети), и будущие subtasks — одной механикой.

## 4. Дизайн

### 4.1. Quick add row — на странице Tasks

Постоянная строка ввода **вверху списка**, в фокусе при открытии страницы.

```
ЗАДАЧИ · завтра                                    27
┌──────────────────────────────────────────────┬────────────────┐
│ + позвонить в банк_                        ⌄ │  Полная задача │
└──────────────────────────────────────────────┴────────────────┘
  □ купить хлеб                                    3 · 15м
  □ дописать отчёт                                 2 · 60м
     ↳ □ собрать цифры                             3 · 15м
     ↳ □ отправить                                 3 ·  5м

Enter      создать и остаться в строке (фокус не уходит)
Alt+→      сделать подзадачей предыдущей созданной
Alt+←      вернуть на уровень выше
⌄ / Ctrl+E раскрыть поля
Esc        снять фокус / закрыть раскрытые поля
```

> 🔴 **Не вешать indent на `Tab`.** `Tab` — клавиша перевода фокуса браузера, а рядом со
> строкой стоят кнопка «Полная задача» и шеврон. `preventDefault()` на `Tab` запирает
> клавиатурного пользователя внутри поля — это keyboard trap, WCAG 2.1.2, ровно на той
> поверхности, где Денис будет жить. Плюс семантика не та: indent действует на **уже
> созданную** задачу, а не на текст в поле. Дефолт — `Alt+→` / `Alt+←` (перенастраивается).

- **Enter создаёт и оставляет фокус в строке.** Это вся суть фичи. Поле очищается,
  созданная задача появляется в списке сверху вниз, фокус не двигается.
- **Кнопка «Полная задача»** в конце строки — открывает существующую модалку целиком,
  с уже введённым текстом в поле title. Ничего не теряется при переключении.
- **Tab** делает только что созданную задачу ребёнком предыдущей. Так строится дерево
  без отдельного режима «создать список»: набрал родителя, Tab, набрал детей.
- Пустой Enter ничего не делает (не создаёт задачу-пустышку).

### 4.2. Раскрытие полей — три уровня

Одна и та же строка, `⌄` раскрывает её постепенно. Простая задача и полная задача —
**одна и та же сущность**, разница только в том, сколько полей видно.

| Уровень | Поля | Как открыть |
|---|---|---|
| 0 — по умолчанию | title | всегда |
| 1 — контекст | priority, due date, estimated_minutes, tags | `⌄` / Ctrl+E |
| 2 — всё остальное | description, contexts, energy, parent, ссылки/источники | `⌄` ещё раз |

**Правило Enter, однозначно:** `Enter` создаёт задачу **только из поля title**. Из любого
другого поля `Enter` ведёт себя нативно (перевод строки в `description`, выбор в `<select>`
priority, подтверждение в date input), а создаёт задачу **только `Ctrl+Enter`**. Оба
шортката настраиваются (§4.5).

> Уровень 2 намеренно оставлен минимальным в этой итерации: `description`, `contexts`,
> `energy`, `parent`. «Место / ссылки / источники» из обсуждения — это **новые колонки**,
> то есть миграция; выносим в отдельный тикет после P1, чтобы не ломать zero-migration.

### 4.3. Глобальный хоткей + модалка

`Ctrl+K` с любой страницы (в т.ч. с календаря) открывает оверлей быстрого захвата —
**тот же самый компонент**, что и строка, только в модалке. Список созданного за сессию
показывается тут же, Esc закрывает.

Один компонент `<QuickAdd/>`, два места вызова. Не два разных кода.

### 4.4. Значения по умолчанию

Быстрая задача получает:

| Поле | Значение по умолчанию | Настраивается |
|---|---|---|
| `status` | `TODO` | нет |
| `due_date` | **завтра** | да |
| `priority` | **3** (из 5) | да |
| `estimated_minutes` | **15** | да |
| `tags`, `contexts` | пусто | через «наследовать фильтры» |

**«Наследовать текущие фильтры» — отдельный toggle, по умолчанию ВЫКЛЮЧЕН.** Когда включён,
новая задача забирает активные фильтры страницы (день, теги, контекст) вместо дефолтов.
Мощно, но неочевидно — поэтому явно выключено и подписано человеческим языком, а не
«apply current filters».

`estimated_minutes = 15` по умолчанию — потому что задачи режутся на 5–15 минут. Это же
даёт бесплатный сигнал на будущее: `estimated_minutes` против `actual_minutes` (колонка уже
есть, Pomodoro в неё пишет) = «правильно ли я режу задачи и насколько недооцениваю».
**Саму рефлексию по estimate-vs-actual в P1 не делаем** — только следим, чтобы данные
писались корректно с первого дня.

### 4.5. Настройки

Новая секция «Быстрое создание задач» в Settings. Хранится в `"user".settings` JSONB —
миграции не нужно:

```json
{
  "quick_task": {
    "default_due": "tomorrow",        // today | tomorrow | none
    "default_priority": 3,            // 1..5
    "default_estimate_minutes": 15,   // null = не ставить
    "inherit_filters": false,
    "keys": {
      "submit": "Enter",
      "submit_expanded": "Ctrl+Enter",
      "expand": "Ctrl+E",
      "global_capture": "Ctrl+K",
      "indent": "Alt+ArrowRight",
      "outdent": "Alt+ArrowLeft"
    }
  }
}
```

Шорткаты настраиваемые, но **дефолты обязаны работать без единого захода в Settings.**

### 4.6. Закрытие задач

- **Чекбокс прямо в списке**, один клик или Пробел на сфокусированной задаче: `TODO → DONE`.
  Карточка не открывается. Toast с **Undo** (паттерн уже есть — Pomodoro его использует).
- **Массовые действия:** Shift+клик выделяет диапазон → «Закрыть» / «Перенести на завтра».
  Закрывает сценарий «не успел сегодня, перекинь всё».
- **Закрытие из Telegram — в P2**, обычным ботом (`bot/internal/handlers/tasks.go` уже
  существует), не notification-ботом.

## 5. Backend

Единственное изменение: **batch-создание**, чтобы 20 задач не были 20 round-trip'ами.

```
POST /api/tasks/batch
{ "tasks": [ {title, priority?, due_date?, estimated_minutes?, tags?, parent_id?}, ... ] }
→ 201 { "data": [ Task, ... ] }
```

- **Частичный успех, не всё-или-ничего.** Одна плохая строка из 20 не должна убивать вставку:
  валидные строки создаются, невалидные возвращаются списком ошибок с индексом строки
  (`{"data": [...], "errors": [{"index": 7, "message": "..."}]}`). Для flow «вставил простыню»
  это то, что нужно; полный откат здесь был бы враждебным.
- Порядок ответа = порядок запроса.
- Валидация как в существующем `CreateHandler` (переиспользуем, не дублируем).
- Лимит 100 задач на запрос — защита от случайной вставки простыни.
- Фронт использует его для «вставить много строк разом»; одиночный Enter по-прежнему
  идёт в обычный `POST /tasks` с optimistic update.

Файлы: `api-go/internal/tasks/handlers.go`, `types.go`, роут в `api-go/cmd/api/main.go`.

### 5.1. Обязательный побочный фикс: T1

`getTasks` (`web/src/api/index.ts:161-168`) кастует snake_case JSON в camelCase-тип **без
конверсии**, поэтому `task.estimatedMinutes` всегда `undefined`. Пока это не починено,
дефолтная оценка времени из §4.4 будет молча теряться при каждом чтении списка.
**T1 входит в P1** — без него фича не работает.

⚠️ Сломан **только путь чтения**. Запись работает: `estimated_minutes` доходит до БД и лежит
там корректно. Существующие данные не испорчены — фронт просто не умеет их прочитать.

## 6. Тестирование

Текущее состояние: 200 тестов / 27 файлов, чистая логика покрыта, React-компонентного
harness **нет** (см. ROADMAP → Engineering Health).

- **Чистая логика → unit-тесты (обязательно):** вычисление дефолтов (`buildQuickTask`),
  наследование фильтров, indent/outdent дерева, парсинг настроек из JSONB с невалидными
  значениями.
- **Batch-эндпоинт → Go-тесты:** порядок ответа, частичный успех при невалидной строке
  (валидные создались, ошибка вернулась с индексом), превышение лимита в 100.
- **UI → руками:** фокус не уходит после Enter, `Alt+→` делает ребёнка, `Esc` не теряет
  набранное, **`Tab` по-прежнему уводит фокус на кнопку** (нет keyboard trap).
  Отдельный пункт в staging-чеклисте P1.

> Компонентный harness (React Testing Library) напрашивается именно здесь, но это отдельное
> решение — тянуть его внутрь P1 значит удвоить объём. Решаем отдельно.

## 7. Порядок реализации

1. T1 — конверсия snake_case → camelCase в `getTasks` + тест (**сначала**, иначе всё врёт)
2. Настройки `quick_task` в JSONB: чтение, дефолты, устойчивость к мусору + тесты
3. `buildQuickTask` — чистая функция дефолтов + тесты
4. `<QuickAdd/>` — строка на Tasks, Enter + фокус, оптимистичный рендер
5. Раскрытие уровней 1 и 2
6. `Alt+→` / `Alt+←` — дерево
7. `POST /tasks/batch` + подключение
8. Чекбокс + Undo в списке
9. Массовое выделение и действия
10. Секция Settings + настраиваемые шорткаты
11. Глобальный `Ctrl+K` (тот же компонент во втором месте)

Пункты 1–4 — уже пригодный к жизни продукт. Дальше по убыванию ценности.

## 8. Открытые вопросы

- **Порядок задач внутри группы.** Сейчас группировка по priority. При 50 задачах в день
  нужен предсказуемый порядок внутри группы — created_at? due_date? Отдельное решение.
- **Уровень 2 «место / ссылки / источники»** требует миграции — тикет после P1.
- **React-компонентный harness** — брать или нет, отдельно от P1.
