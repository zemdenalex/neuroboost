## 1. 🔴 Токен бота уходит в лог API — фикс 14.08 закрыл читателя, но не провод

**Что код обязан делать.** `bot/internal/logsafe` существует ровно затем, чтобы токен не попал
никуда, что этот процесс записывает. `CLAUDE.md` gotcha 14 утверждает: «✅ **Свой код больше не
течёт** (14.08): три места, печатавшие `%v` от `*url.Error` с полным URL, идут через
`logsafe.Redact`».

**Где рвётся — цепочка из трёх адресов:**

```
bot/internal/notifier/notifier.go:77   reason = sendErr.Error()        ← СЫРОЙ текст
bot/internal/notifier/notifier.go:78   log.Printf(..., logsafe.Redact(sendErr))  ← а вот тут редакция
bot/internal/api/client.go:254         json.Marshal({"delivered":…, "error": sendErr})
api-go/internal/reminders/service.go:247  svcLog.Warn(..., slog.String("error", req.Error))
```

`sendErr` — это `*url.Error` от Telegram-клиента, его `Error()` содержит
`https://api.telegram.org/bot<TOKEN>/sendMessage`. На строке 78 он редактируется. На строке
**77, на строку выше**, тот же самый объект превращается в строку **без** редакции, уезжает по
сети в `/api/svc/notifications/{id}/ack` и печатается структурным логом API.

**Чем подтверждено.** Чтением трёх файлов по адресам выше плюс отрицательным поиском:
`grep -rn "logsafe" api-go/` — **ноль вхождений**. Пакет `logsafe` живёт в модуле `bot/`, у
`api-go` редакции нет вообще нигде. Это не «пропущенный вызов», а структурная дыра: чинить
придётся либо на отправке (`notifier.go:77` → `logsafe.String(sendErr.Error())`), либо заводить
редакцию в `api-go`.

**Что из этого следует.** Утверждение gotcha 14 «свой код больше не течёт» **ложно**. Хуже
исходного дефекта: раньше токен лежал в логах бота (о них хотя бы знали и читали через `sed`),
теперь он ещё и в логах API, где `sed`-правило не применяют, потому что «это же не бот».
Ротация токена, числящаяся в `CLAUDE.md` как «всё равно нужна», после этого разбора обязательна.

## 2. 🔴 Две копии одного отсоединённого occurrence на общем календаре

**Что код обязан делать.** Комментарий `occurrence.go:175–176`: «re-editing an occurrence that
is already detached must point the exception at the new replacement rather than fail on the
unique key». То есть повторное отсоединение того же occurrence обязано **заменять**
replacement, а не плодить второй.

**Где рвётся.** Ключ конфликта — `ON CONFLICT (user_id, event_id, occurrence)`
(`occurrence.go:180`), и он совпадает с `UNIQUE (user_id, event_id, occurrence)` из
`api-go/migrations/000001_baseline.up.sql:145`. **`user_id` входит в ключ.**

А читаются исключения без `user_id`: `events/recurrence.go:244` фильтрует по
`e.calendar_id = ANY($1)` — и это сделано намеренно, комментарий на `recurrence.go:221–225`
объясняет, что исключения суть общее состояние серии.

Условия разошлись: **пишется по пользователю, читается по календарю.**

**Последовательность, на которой ломается:**

| шаг | кто | что |
|---|---|---|
| 1 | член A общего календаря | двигает occurrence 2026-09-03 → строка exception (A, ev, 03.09) + replacement A |
| 2 | член B того же календаря | двигает тот же occurrence → `ON CONFLICT` **не срабатывает** (другой `user_id`) → строка exception (B, ev, 03.09) + replacement B |
| 3 | любой из них открывает неделю | `fetchExceptions` вернёт обе строки → occurrence скрыт **один раз**, а `listEvents` подберёт **оба** replacement (у них нет rrule и они попадают в окно) |

**Результат:** вместо одного перенесённого события на календаре два, и это состояние
самостоятельно не рассасывается.

**Живой сегодня.** Не ждёт slice 3: два пишущих члена одного календаря создаются уже сейчас —
`calendars/crud.go:299`, `TransferOwnership` понижает прежнего владельца до `editor`, оставляя
нового владельца рядом. Оба проходят `WritableIDsFor`.

**Чем подтверждено.** Схема (`000001_baseline.up.sql:145`), ключ конфликта
(`occurrence.go:180`), отсутствие `user_id` в чтении (`recurrence.go:239–245`), достижимость
двух editor/owner (`crud.go:290–310`). Живого воспроизведения нет — нужен Postgres с двумя
пользователями; механизм и адреса полные.

## 3. 🔴 `detachOccurrence` пишет по праву чтения

**Что код обязан делать.** Правило от 15.08: функция, меняющая `event` или `task`, скоупится
через `calendars.WritableIDsFor`. Отсоединение occurrence — это (а) **вставка новой строки
`event`** и (б) **вставка `event_exception`, скрывающей occurrence у всех членов календаря**.
Обе — записи в чужую серию.

**Где рвётся.** Проверки доступа в этом пути нет ни одной, кроме чтения:

```
events/handlers.go:268   loadOccurrence(ctx, userID, targetID, occDate)
  → occurrence.go:44     getEvent(ctx, userID, parentID)
    → handlers.go:751    calendars.CalendarIDsFor(ctx, userID)   ← право ЧТЕНИЯ
events/handlers.go:294   detachOccurrence(...)   ← пишет, ничего не проверив
```

Три вызывающих места, все три одинаковы: `handlers.go:294` (Update), `:469` (Move), `:550`
(Resize). В самой `detachOccurrence` (`occurrence.go:136–192`) строк `WritableIDsFor` нет —
проверено чтением файла целиком.

**Что из этого следует.** В день, когда появится viewer-членство, получивший право **читать**
общий календарь сможет через `PATCH /api/events/{id}:{date}?scope=occurrence` скрыть чужое
повторяющееся событие и подменить его своей строкой. Для остальных членов это выглядит как
«владелец перенёс встречу». Ровно тот класс дефекта, который работа 15.08 объявила закрытым.

## 5. 🟡 TOCTOU: родитель переехал между проверкой и вставкой

Задание спрашивало это прямо. Ответ:

```
T:   events/handlers.go:751   calIDs := CalendarIDsFor(userID)   — список на момент T
T:   ...                       SELECT … FROM event WHERE id=$1 AND calendar_id = ANY(calIDs)
T+1: occurrence.go:148        SELECT calendar_id FROM event WHERE id = $1   — свежее чтение,
                                                                              внутри своей tx
T+1: occurrence.go:154        INSERT INTO event (…, calendar_id, …)
```

Календарь, в который пишется новая строка, **перечитывается заново** и с проверенным на шаге T
списком не сверяется. Если между T и T+1 кто-то выполнил `PATCH /api/events/{id}` с
`calendar_id` (эта возможность появилась 15.08, см. `events/handlers.go:261`), вставка уйдёт в
новый календарь, к которому вызывающего не проверяли вовсе.

Комментарий `occurrence.go:143–146` объясняет, **почему** наследуется календарь родителя, и он
прав по существу: иначе отсоединение из общего календаря утащило бы occurrence в личный. Он
просто не перепроверяет доступ к тому, что унаследовал.

Окно узкое, эксплуатация требует гонки — поэтому 🟡, а не 🔴. Но чинится тем же движением, что
и §3: `WritableIDFor(ctx, userID, calendarID)` после строки 148, внутри той же транзакции.

## 6. `PersonalIDFor` / `WritableIDFor` — что держит и что нет

### 6.1 🟢 Гонка двух одновременных вызовов — держит

Комментарий `store.go:110–116` описывает механизм верно, и индекс действительно такой, как
обещано: `api-go/migrations/000012_calendars.up.sql:37–39` —

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_calendar_one_personal_per_owner
    ON calendar (owner_id) WHERE kind = 'personal';
```

Частичный уникальный индекс по `owner_id`, ровно как сказано. Два одновременных вызова: оба
промахиваются, оба делают `INSERT … ON CONFLICT DO NOTHING`; Postgres берёт speculative
insertion lock, второй ждёт первого и после его коммита не делает ничего; оба перечитывают
`readCalendarID` и получают один и тот же id; оба вставляют `calendar_member` с конфликтом по
первичному ключу `(calendar_id, user_id)` — идемпотентно. Двух календарей не будет.

### 6.2 ⚠ `ON CONFLICT DO NOTHING` без цели конфликта — сегодня работает, завтра тихо перестанет

Форма без `(owner_id) WHERE kind = 'personal'` ловит **любое** нарушение уникальности на
`calendar`, а не то, которое имелось в виду. Сегодня других уникальных ограничений у таблицы
нет (`000012_calendars.up.sql:8–15` — только PK по `gen_random_uuid()`), поэтому поведение
совпадает с обещанным.

Механизм отказа, если появится ещё одно: скажем, `UNIQUE (owner_id, name)`. Тогда у
пользователя с общим календарём, названным «Мой календарь», `INSERT` молча не сработает,
`readCalendarID` (`store.go:172`) вернёт `pgx.ErrNoRows`, и `PersonalIDFor` отдаст наверх
ошибку «нет строк» на пути, который создан именно чтобы такой ошибки не было. Свидетеля на
живом коде нет — записано как **подозрение с механизмом**. Цена страховки — дописать цель
конфликта, она уже известна.

### 6.3 🟡 «Календарь есть, членства нет» чинится; «членство есть, но `invited`» — не чинится

`readHealthyPersonalID` (`store.go:157–167`) считает состояние здоровым только при
`m.status = 'active'`. Значит членство со статусом `invited` даёт промах → запускается путь
восстановления → `INSERT INTO calendar_member … ON CONFLICT DO NOTHING` (`store.go:143–149`)
натыкается на первичный ключ `(calendar_id, user_id)` и **не делает ничего** → функция
возвращает id, как будто починила.

Не починила: `AccessibleIDs` (`access.go:32–40`) пропускает только `active`, поэтому
`CalendarIDsFor` по-прежнему вернёт пусто и владелец не увидит ни одного своего события. При
этом каждый следующий вызов повторит тот же бесполезный круг.

Достижимость сегодня: строк, создающих членство со статусом `invited`, в коде нет
(`grep -rn "StatusInvited" api-go/` даёт только объявление константы и её употребление в
`CHECK`-константах) — приглашения это slice 3. Латентно.

Лечится одним движением: `ON CONFLICT (calendar_id, user_id) DO UPDATE SET role = 'owner',
status = 'active'` — то есть тем же приёмом, который уже применён в `occurrence.go:180`.

### 6.4 🟡 `readHealthyPersonalID` не проверяет `role`

Условие соединения — `m.user_id = c.owner_id AND m.status = 'active'`, **без** `m.role`.
Членство `role = 'viewer'` на собственном личном календаре прошло бы как здоровое, и тогда
`PersonalIDFor` вернул бы календарь, в который `WritableIDsFor` (`store.go:74`, фильтр
`role IN (owner, editor)`) писать не разрешает. Создание события без явного календаря
(`WritableIDFor` с пустым `calendarID`, `store.go:195`) при этом **обходит проверку роли
вовсе** — оно доверяет `PersonalIDFor`.

Достижимость сегодня: нулевая. Единственное место, понижающее роль, — `TransferOwnership`
(`crud.go:299`), а личный календарь передать нельзя (`crud.go:267–269`,
`ErrCalendarIsPersonal`). Записано как латентный разрыв инварианта, не как живой дефект.

### 6.5 🟢 `WritableIDFor` — держит

`store.go:194–218`: пустой id → личный календарь; непустой — проверяется по членству со
статусом `active` и ролью `owner`/`editor`; `22P02` (не-UUID) и `ErrNoRows` сводятся к
`ErrCalendarNotFound`, чтобы 403 не подтверждал существование чужого календаря. Замечаний нет.

## 7. 🟢 Порядок middleware вокруг `/api/import` — держит

**Что проверялось.** Что групповой лимит 1 MiB не оборачивает более широкий 32 MiB.

**Как перечислялось (чтобы отрицательный результат был проверяемым).** Прочитан
`api-go/cmd/api/main.go` целиком в части маршрутов; все регистрации маршрутов такие и только
такие:

| строки | что | лимит |
|---|---|---|
| 84 | `GET /api/health` вне групп | нет — GET без тела |
| 94–104 | группа: auth + public feedback | `PublicBodyLimit` 64 KiB |
| 110–119 | `r.Route("/api/svc")` | rate limit → `ServiceBodyLimit` 32 KiB → service token |
| 122–184 | группа JWT | `AuthedBodyLimit` 1 MiB |
| 194–198 | **отдельная** группа, только `POST /api/import` | `ImportBodyLimit` 32 MiB |
| после 198 | маршрутов нет — `ListenAndServe` | — |

`POST /api/import` зарегистрирован **ровно один раз**, в группе 194–198, и в группе 122–184 его
нет (там только `GET /api/export`, строка 183, с явным комментарием). Вложения групп нет, значит
1 MiB до 32 MiB не добирается. Комментарий `main.go:186–193` описывает именно эту причину и
описывает верно.

Порядок внутри `/api/svc` тоже правильный: rate limit раньше проверки токена, значит поток
запросов с плохим токеном отбивается дёшево.

## 8. 🟡 413 отличается от 400 в одном месте из двадцати пяти

`util.RespondDecodeError` (`util/response.go:58–66`) устроена верно: `errors.As` на
`*http.MaxBytesError` (это правильный тип для `MaxBytesReader`), 413 с указанием лимита из
`maxErr.Limit`, иначе прежний 400.

**Где рвётся.** Она вызывается **один раз** во всём `api-go`:
`internal/export/handlers.go:141`. Мест, декодирующих тело запроса,
`grep -rn "NewDecoder(r.Body).Decode" api-go/internal api-go/cmd` (без `_test`) — **25**.
Остальные 24 отвечают вручную, например `events/handlers.go:434`, `:520`,
`tasks/handlers.go:316`: `RespondError(w, 400, "INVALID_REQUEST", "Invalid request body")`.

**Что из этого следует.** Ровно та болезнь, которую `bodylimit.go:16–19` описывает как причину
завести отдельные лимиты — «пользователь видит 400 Invalid request body и не может понять, что
тело просто велико», — вылечена только для `/api/import`. Для всех остальных маршрутов
превышение 1 MiB по-прежнему выглядит как битый JSON. Безопасности это не трогает; трогает
диагностируемость.

⚠ Формально комментарий `bodylimit.go:42–44` честен («Handlers that **want** to answer 413…»),
поэтому это 🟡, а не 🔴. Но 1 из 25 — это не «часть обработчиков предпочла 400».

## 9. ⚪ `bodylimit.go:49–52` — комментарий про не тот код

```go
// GET and DELETE carry no body worth capping, and wrapping them
// costs an allocation per request for nothing.
if r.Body != nil && r.Body != http.NoBody {
```

Условие проверяет **тело**, а не **метод**. На серверной стороне `net/http` `r.Body` не бывает
nil и практически не бывает `http.NoBody` (для запроса без тела ставится `http.NoBody` только в
клиентских запросах; сервер подставляет `http.noBody`-читатель другого типа), так что GET и
DELETE оборачиваются наравне со всеми. Поведение безвредное, объяснение неверное. Дефект
изложения — но именно такие комментарии потом читаются как действующее ограничение.

## 10. `logsafe` — что regexp пропустит

`tokenPattern = bot[0-9]+:[A-Za-z0-9_-]+` (`redact.go:24`).

**Что ловит корректно.** Формат токена Telegram — `<цифры>:<35 символов A-Za-z0-9_->`, в URL
всегда с префиксом `bot`: `…/bot123:AA…/getMe`, `…/file/bot123:AA…/photo.jpg`. `/` обрывает
класс символов, поэтому следующий сегмент пути не съедается. Проверено тестом
`redact_test.go:18` через настоящий `*url.Error`, включая двойное оборачивание (`:41`) и

**Что пропустит:**

1. **Токен без префикса `bot`.** Якорь на `bot` — сознательный размен (иначе редактировалось бы
   всё с двоеточием), но он означает: любая печать самого `cfg.TelegramToken` пройдёт насквозь.

   `cmd/main.go:27`, `:42`, `:49`, ни одной в форматной строке. Проверено.
2. **`debug.Stack()` не редактируется** — `notifier.go:48` и `cmd/main.go:130`. Go печатает
   аргументы функций машинными словами, не содержимым строк, поэтому практический риск низкий;
   записано как оговорка, не как дефект.
3. **🔴 Асимметрия в двух recover'ах.** `cmd/main.go:130` пропускает значение паники через
   `logsafe.String(fmt.Sprint(r))`. `notifier/notifier.go:48` печатает `%v` от `r` **сырым**.
   Один и тот же вид данных, два разных решения, разница ничем не объяснена — по собственному
   стандарту проекта это пропуск.
4. **Логи самой библиотеки.** `tgbotapi` пишет свои ошибки собственным логгером;
   `grep -rn "SetLogger" bot/` — **ноль вхождений**, значит `getUpdates`-ошибки библиотеки идут
   мимо `logsafe` целиком. `CLAUDE.md` gotcha 14 это признаёт; фиксирую, что подавитель
   (`tgbotapi.SetLogger`) существует и не подключён.

## Контроли, которые не могли отказать

1. 🔴 **`TestWritesScopeByWritableCalendars` зелёный при живых §3 и §4.** Не рассуждение —
   прогон: `cd api-go && go test ./internal/calendars/ -run TestWritesScopeByWritableCalendars -v`
   → `--- PASS`, при том что `detachOccurrence` вставляет `event`, а доступ проверен по чтению.
   Две независимые причины, и обе структурные:

   - **`writescoping_test.go:135`**: `if !strings.Contains(fn, "CalendarIDsFor") &&
     !strings.Contains(fn, "WritableIDsFor") { continue }`. `detachOccurrence` не упоминает ни
     одного из имён — её проверка доступа сделана **в другой функции** (`getEvent`). Тест
     смотрит на одну функцию за раз и межфункциональную проверку доступа увидеть не может
     в принципе.
   - **`writescoping_test.go:140`**: нарушителем считается функция, в тексте которой встретился
     `CalendarIDsFor`. `scheduleTask` содержит `WritableIDsFor` — но для **другого** запроса
     (обновление статуса задачи, `tasks/handlers.go:688`), а не для вставки события. Тест
     засчитывает её как просканированную и чистую. То есть присутствие правильного имени
     где-нибудь в теле функции работает как индульгенция.

   Это тот же класс, что §1 разбора 15.08: контроль зелен при наличии дефекта. Разница в том,
   что тогда дефект был гипотетической пробой, а сейчас — двумя настоящими функциями в проде.

2. 🔴 **Тесты `logsafe` проверяют только сам хелпер, ни одного места вызова.**
   `redact_test.go` целиком состоит из вызовов `Redact`/`String` с рукотворными входами. Все
   пять тестов остаются зелёными при `reason = sendErr.Error()` на `notifier.go:77` — то есть
   при живой утечке §1. Тест доказывает, что функция работает, и ничего не говорит о том,
   зовут ли её там, где надо. Контроль такого рода нужен по образцу `writescoping_test.go` —
   сканирующий, а не unit'овый.

3. 🟡 **`scheduleTask`, `tasks/handlers.go:689` и `:695–697`** — две проверки, которые не могут
   сообщить об отказе:
   ```go
   calIDs, err := calendars.WritableIDsFor(ctx, userID)
   if err == nil {
       _, err = db.Pool.Exec(ctx, `UPDATE task SET status = 'SCHEDULED' …`)
   }
   if err != nil {
       // Non-fatal, event was created
   }
   ```
   Ветка `if err != nil` **пуста** — комментарий стоит там, где должна быть обработка. Отказ
   `WritableIDsFor` пропускает `UPDATE` целиком и не оставляет ни строки в логе. Наблюдаемый
   результат: событие создано, задача осталась в прежнем статусе, причина не записана нигде.

4. ⚪ **`TestInsertsIntoEventOrTaskSetCalendarID`** (`scoping_test.go:168`) проверяет ровно то,
   что заявляет — присутствие `calendar_id` в списке колонок, — и §3/§4 поймать не может по
   построению. Не дефект теста; отмечено, чтобы его зелёный не читался как «вставки в порядке».

5. 🟡 **DB-тестов у `calendars` нет вовсе.** `store.go` — гонки, самолечение, роли — покрыт
   только статическими сканерами и чистой `AccessibleIDs`. §6.1, §6.3, §6.4 поэтому проверены
   чтением и знанием Postgres, а не прогоном. Прежняя оговорка из разбора 15.08 («DB-тесты
   молча `t.Skip` без `DATABASE_URL`») здесь даже не применима — скипать нечего.
