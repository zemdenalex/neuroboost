## 1. 🔴 `writescoping_test.go` не видел записи, чья SQL лежит в константе

**Что тест обязан делать.** Функция, меняющая `event` или `task`, обязана скоупиться через
`calendars.WritableIDsFor` (owner + editor), а не через `CalendarIDsFor` (всё читаемое). Правило
введено 15.08 после того, как выяснилось, что десять мест записи давали право писать всякому,
кому дали читать.

**Где рвалось.** `api-go/internal/calendars/writescoping_test.go:79` (до правки): функция
считалась «меняющей», только если **внутри неё самой** нашёлся backtick-литерал с
`UPDATE|DELETE FROM|INSERT INTO event|task`. Функция вида

```go
const probeSQL = `UPDATE task SET title = $1 WHERE id = $2 AND calendar_id = ANY($3)`

func probeWriteViaConst(ctx context.Context, userID, taskID string) error {
    calIDs, err := calendars.CalendarIDsFor(ctx, userID)   // ← право чтения
    ...
    _, err = db.Pool.Exec(ctx, probeSQL, "x", taskID, calIDs)
}
```

своего литерала не имеет, поэтому **не сканировалась вовсе**.

**Чем подтверждено.** Не рассуждением — пробой. Файл выше положен в `internal/tasks/`, тест
прогнан: `ok neuroboost/api-go/internal/calendars` — прошёл, ничего не заметив. Порог
`minWriteFunctionsScanned` тоже не спас: он считает только просканированные функции, а эта в
счёт не попадала.

**Почему это важнее обычного бага.** Вынести запрос в именованную константу — обычный, скорее
похвальный рефакторинг. Контроль, который такой рефакторинг молча выключает, — это контроль,
который **будет** выключен, и никто не заметит момента.

**Починено 15.08.** Тест собирает пакетные идентификаторы, чьё backtick-значение меняет
`event`/`task` (`sqlConstRe`), и считает «меняющей» всякую функцию, упоминающую такой
идентификатор (по границе слова, чтобы `updateSQL` не ловился на `updateSQLBuilder`).
Проверено обеими сторонами: без пробы — `ok`, с пробой — падение с именем функции.

## 2. 🟡 Тот же тест мог ослепнуть на SQL с `//` внутри

`lineCommentRe` был `(?m)//.*$` — без якоря. Такой шаблон срабатывает и **внутри строки**:
блок SQL, содержащий `'http://…'`, обрезался бы по этому слэшу вместе со своим закрывающим
backtick'ом, и после этого не опознавался бы как SQL вообще.

Свидетеля на живом коде нет — таких запросов сейчас в репозитории не нашлось (искал `//` внутри
backtick-блоков). Записано как **подозрение с механизмом**, а не как найденный дефект.

**Починено превентивно:** якорь `^\s*//`. Размен осознанный: теперь возможен ложный
**положительный** (комментарий в конце строки, упоминающий хелпер), но невозможен ложный
отрицательный. Шумный контроль читают, слепому — верят.

⚠ Ровно этот шаблон уже давал ложный положительный: первая версия теста прочитала комментарий,
**объясняющий** починку `reminders/action.go`, как саму нарушающую строку. Якорь по началу
строки этот случай по-прежнему покрывает.

## 3. 🔴 Правка настроек теряется, если ответ сервера обгоняет следующую правку

**Что код обязан делать.** Секции `/settings` правят локальное состояние и сохраняют его
debounce'ом (300 мс, `web/src/lib/autoSave/debouncedSaver.ts`). Сохранение уходит через
`updateSettings` (`web/src/contexts/AuthContext.tsx:204`), который делает
`{...prevSettings, ...patch}` и шлёт **весь** объект настроек, затем `setUser(updatedUser)`.

**Где рвётся.** Девять из тринадцати секций пересобирают своё состояние эффектом на
**идентичность объекта `user`**:

```
web/src/pages/Settings/sections/RemindersSection.tsx:40   useEffect(..., [user])
```
и так же в `QuickTaskSection`, `LayoutStyleSection`, `WorkHoursSection`, `UIScaleSection`,
`RegionalSection`, `RecurringScopeSection`, `MobileNavSection`, `FeatureTogglesSection`
(проверено grep'ом по `[user]`).

`setUser` отдаёт **новый объект на каждое сохранение**, поэтому эффект срабатывает после
каждого ответа сервера — в том числе когда локально уже лежит более свежая, ещё не отправленная
правка.

**Последовательность, на которой ломается** (времена условные, важен порядок):

| t | что происходит | состояние в UI | что в очереди сохранения |
|---|---|---|---|
| 0 | правка **A** | A | A, отправка в 300 |
| 300 | PATCH(A) ушёл | A | пусто |
| 350 | правка **B** | B | B, отправка в 650 |
| 500 | пришёл ответ на A → `setUser` → эффект | **A** ← B стёрт с экрана | B |
| 600 | правка **C**, посчитанная от того, что на экране | A+C | **A+C затирает B** |
| 650 | PATCH(A+C) | A+C | — |

**B потеряна безвозвратно.** Не «мигнула»: `replace()` строит следующее значение от
`latest.current`, а `latest.current` к этому моменту уже перезаписан ответом сервера; и
`schedule()` заменяет ожидающий patch целиком, потому что ключ один и тот же — `reminders`.

Без шага 600 дефект самоисправляется через ~150 мс (B долетит и вернётся), то есть выглядит как
мигание. Именно поэтому он и доживёт: в большинстве случаев он проявляется как рябь, а теряет
данные только когда пользователь печатает достаточно быстро.

**Чем подтверждено.** Чтением: `AuthContext.tsx:204–212` (полная замена + `setUser`),
`RemindersSection.tsx:40–48` (эффект + `latest.current = reminders` на каждый рендер),
`debouncedSaver.ts` (`schedule` заменяет ожидающий patch). Живого воспроизведения **нет** —
это подозрение с механизмом и с точными адресами, но без прогона.

**Что из этого следует.** Лечится сменой зависимости эффекта с объекта `user` на `user?.id`:
пересобирать состояние надо при смене **аккаунта**, а не при каждом ответе сервера. Цена —
настройки, изменённые на другом устройстве, не подхватятся без перезагрузки страницы; сейчас
они и так не подхватываются ничем, кроме собственного сохранения.

🔴 Правка затрагивает девять секций, и у `/settings` **нет ни одного unit-теста**. Делать её
надо вместе с тестом на приведённую выше последовательность, иначе это замена одного
непроверенного поведения на другое.
