## Форма мержа — проверено пробным слиянием, ветки не тронуты

`git merge-tree --write-tree main develop` (считает результат, ничего не пишет):

| Что | Итог |
|---|---|
| Перемотка (fast-forward) | ❌ нет — у `main` 3 собственных коммита |
| **Конфликты в коде** | 🟢 **ноль.** `Calendar.tsx` слился автоматически |
| Конфликты в документах | 🟡 **5**, все `add/add` |
| Объём релиза | 446 файлов, +33 355 / −2 071 |

**Пять конфликтов — тривиальные.** Это один и тот же файл, созданный независимо на обеих
ветках, поэтому у git нет общего предка и он отказывается выбирать сам. Разница между версиями
— **ровно одна строка**: паспорт, который на `develop` проставил `docs_passport.py`.

Во всех пяти брать версию `develop`:

```
docs/superpowers/plans/2026-06-01-pomodoro-focus-timer.md
docs/superpowers/plans/2026-06-17-hints-cores.md
docs/superpowers/plans/2026-06-17-onboarding-cores.md
docs/superpowers/specs/2026-06-01-pomodoro-focus-timer-design.md
docs/superpowers/specs/2026-06-17-show-hints-reveal-design.md
```

```bash
git checkout --theirs <каждый из пяти>   # при merge develop → main
```

✅ **Хотфикс воскресенья не потеряется.** `ed69712` («календарь пуст по воскресеньям») живёт
только на `main` как коммит, но его содержимое уже есть в `develop`: `weekRange.ts` **побайтово
идентичен** на обеих ветках, `Calendar.tsx` использует `computeWeekRange`. Проверено сравнением
файлов между ветками, а не по журналу.

## 🔴 Что сломается после мержа, если не сделать заранее

### 1. Уведомления на проде не поедут — нет `SERVICE_TOKEN`

Измерено: в `/opt/neuroboost/.env` на `62.76.228.106` **ноль строк** `SERVICE_TOKEN=`.
Сегодня это незаметно, потому что ручек `/api/svc` на проде вообще нет:

```
prod  /api/svc/notifications/pending → 404
stage /api/svc/notifications/pending → 401   ← ручка есть, нужен токен
```

После мержа ручки появятся и начнут отвечать 401 боту. Порядок:

```bash
ssh root@62.76.228.106
cd /opt/neuroboost
# дописать SERVICE_TOKEN=<секрет> в .env
docker compose up -d --force-recreate api      # 🔴 НЕ restart — он не перечитывает .env
```

Тот же секрет — в `/opt/neuroboost-bot-prod/.env` на `185.214.10.107`, тем же способом.

### 2. Прод-бот тоже деплоится руками

Бот **не входит в CI** и живёт на другой машине. После мержа API станет новым, а бот останется
вчерашним, и это выглядит как «уведомления сломались», а не как «бот не обновлён».

```bash
tar -czf - -C bot . | ssh root@185.214.10.107 \
  'rm -rf /opt/neuroboost-bot-prod/src && mkdir -p /opt/neuroboost-bot-prod/src && tar -xzf - -C /opt/neuroboost-bot-prod/src'
ssh root@185.214.10.107 'cd /opt/neuroboost-bot-prod && docker compose up -d --build bot'
```

⚠ На этой машине рядом живёт боевой exit-узел Nivium (`remnanode`, `caddy-selfsteal`) — трогать
только свои контейнеры.

### 3. Четыре миграции применятся на старте

Измерено: прод стоит на **000008**, в репозитории **12**. Применятся `000009`…`000012`.

🔴 **`000012` — это календари.** Она заводит по личному календарю на каждую строку `user`
и раскладывает по ним существующие события. Отсюда следующий пункт.

### 4. Раздвоение личности — 7 строк `user`, и это решается ДО миграции

Измерено на проде:

| `email` | `tg_id` | строк |
|---|---|---|

| нет | **есть** | **1** |

Всего в базе 23 события и 7 задач. Одна из этих строк — твой Telegram-вход, отдельный от
почтового. **После `000012` у тебя станет два личных календаря**, и события разъедутся между
ними по признаку, кто их создал.

✅ **Скрипт готов и проверен: `scripts/merge-identities.sql`.**

🔴 **Уточнение, снимающее половину сложности:** порядок из
`docs/superpowers/plans/2026-08-11-p3-slice2-inherited-debt.md` §8 (с переносом календарей)
описывает случай **после** миграции 000012. Проверено: на проде `to_regclass('public.calendar')`
даёт `NULL` — таблицы нет. **Пока миграция не применена, слияние — это простой перенос строк**,
без календарей и без столкновения каскадов.

Проверено на **копии прода** (отдельная база `merge_test` из `pg_dump`, удалена после):
