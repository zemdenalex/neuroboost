списком «Приглашения» в самом приложении и жмёт «Принять». Ни писем, ни токенов, ни ссылок.

## Что входит в работу

### Срез 0 — слияние личностей (предусловие)

| Кусок | Размер |
|---|---|
| Ветка в `createUserFromTelegram`: `tg_id` не найден → искать по email из Telegram (его отдаёт не всякий аккаунт) → нашли: дописать `tg_id` существующему; не нашли: создать | ~полсессии |
| Ручная привязка в `/profile` для тех, у кого email в Telegram скрыт: «привязать Telegram» под уже вошедшим аккаунтом — единственный надёжный путь | ~полсессии |
| **Миграция продовых данных**: найти пары, слить, перенести события/задачи/настройки на выжившую запись | 🔴 отдельно, см. ниже |
| Тесты: слияние идемпотентно; чужой `tg_id` не приклеивается к чужому email | ~полсессии |

🔴 **Миграция данных — не код, а решение.** Слияние двух записей переносит события, задачи,
рефлексии и настройки; какие настройки выживают при конфликте — твой выбор, а не мой. И это
необратимо без бэкапа. **Это то место, где я обязан остановиться и спросить.**

### Срез 3 — собственно приглашения

| Кусок | Размер |
|---|---|
| Миграция: токен приглашения (`calendar_member.status='invited'` уже есть с `000012`) | немного |
| `POST /api/calendars/:id/invites` — по email, с отказом при 0 или >1 совпадении | ~сессия |
| `POST /api/calendars/invites/:token` — принять, `invited` → `active` | ~полсессии |
| `DELETE /api/calendars/:id/members/:userId` — исключить или выйти самому | ~полсессии |
| UI: пригласить из панели календарей, экран принятия, список участников | ~сессия |
| e2e: создал → пригласил → принял → **оба** видят → второй подвинул → у первого сдвинулось | ~полсессии |

**Итого:** срез 0 ≈ полторы сессии кода **плюс решение по данным**; срез 3 ≈ три с половиной
сессии. Вместе — примерно **пять сессий**, и первая из них упирается в твой ответ.

## 🟡 Чего это НЕ даёт

Даже после среза 3 общий календарь ещё не работает целиком:

- **срез 4** — события и задачи в общем календаре, признак `is_shared` (сейчас событие всегда
  попадает в твой личный);
- **срез 5** — персональные напоминания: сканер должен дать **две** строки на одно общее
  событие, с разными смещениями для каждого участника. Сейчас смещения лежат на событии, а не
  на паре «событие + человек».

То есть «пригласить» без среза 5 означает: вы оба видите событие, но напоминание получит
только один. Это стоит знать до того, как решать порядок.

## Мой ответ на вопрос «входит ли это в релиз»

**Изменился вместе с фактами.** Утром я говорил «нет», и единственной причиной была
необратимая операция над продовой таблицей пользователей. Такой операции не требуется.

Что остаётся верным: `develop` уже на 287 коммитов впереди прода, и смешивать «выкатили
полгода работы» с новой функцией — значит при поломке иметь две возможные причины вместо
одной. Поэтому предлагаю порядок, а не отказ:

1. Выпустить то, что есть (релиз давно назрел).
2. Срез 3 отдельно, на `develop`, с проверкой на staging вдвоём с Lizok.
3. Срез 4 сразу за ним — без него общий календарь виден, но писать в него нельзя.
