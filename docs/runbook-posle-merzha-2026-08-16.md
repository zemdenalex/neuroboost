## §1. Проверка миграций после наката

Прод стоял на **000008**, в репозитории **13**. Накатятся `000009`…`000013` — пересчитать перед
началом: `ls api-go/migrations/*.up.sql | wc -l`.

Из пятерых **только `000013` трогает данные**, остальные меняют схему. Поэтому проверок три, и
третья — про неё.

```bash
ssh root@62.76.228.106
docker exec -it neuroboost-prod-db psql -U neuroboost -d neuroboost
```

⚠ Имя контейнера и пользователя подставь по факту: `docker ps --format '{{.Names}}'` и
`grep POSTGRES /opt/neuroboost/.env`. Ниже — сами запросы.

### 1.1 Докуда дошли миграции

```sql
SELECT version, dirty FROM schema_migrations;
```

Ожидание: `version = 13`, `dirty = false`.

🔴 **`dirty = true` — это не «почти получилось».** golang-migrate ставит его перед применением и
снимает после; `true` означает, что миграция упала на середине и **следующий старт API откажется
мигрировать вообще**. Лечится только руками: понять, что именно не доехало, доделать, затем
`UPDATE schema_migrations SET dirty = false, version = <N>`. Не делать этого вслепую.

### 1.2 Схема стала такой, какой обещано

```sql
-- должно вернуть event_exception_series_occurrence_key (и НЕ ..._user_id_...)
SELECT conname FROM pg_constraint
 WHERE conrelid = 'event_exception'::regclass AND contype = 'u';
```

Если вернулось старое имя `event_exception_user_id_event_id_occurrence_key` — `000013` не
применилась, а `detachOccurrence` уже ждёт нового ключа и будет падать с
`there is no unique or exclusion constraint matching the ON CONFLICT specification`.

### 1.3 Дублей не осталось — единственная проверка про ДАННЫЕ

```sql
-- должно вернуть 0 строк
SELECT event_id, occurrence, count(*)
  FROM event_exception GROUP BY 1, 2 HAVING count(*) > 1;
```

`000013` схлопывает дубли (оставляя самый свежий) и удаляет замены проигравших строк, **до** того
как добавить ограничение. Если бы дубли остались, добавление ограничения упало бы и мы увидели
бы `dirty = true` в 1.1 — то есть этот запрос подтверждает уже случившееся, а не проверяет
впервые. Прогнать всё равно: он стоит секунду и отвечает на вопрос «сколько данных она удалила».

Дублей на проде быть **не должно вовсе**: они возможны только на общем календаре с двумя
пишущими членами, а общих календарей там пока нет — `000012` применяется в этой же пачке.
Если запрос что-то вернул, значит моё рассуждение неверно, и это надо разобрать, а не списать.

### 1.4 Личные календари завелись всем

```sql
-- должно вернуть 0: каждому пользователю положен ровно один личный календарь
SELECT count(*) FROM "user" u
 WHERE NOT EXISTS (
   SELECT 1 FROM calendar c
    WHERE c.owner_id = u.id AND c.kind = 'personal');
```

Это про `000012`. Пользователь без личного календаря не увидит своих событий — но это
самолечится при первом же обращении (`calendars.PersonalIDFor`), так что ненулевой ответ здесь
не авария, а повод зайти в веб под этим аккаунтом и посмотреть.

## §2. Пересборка прод-бота

Бот **не входит в CI** и живёт на **другой машине**, чем API. После мержа API станет новым, а
бот останется вчерашним — и выглядит это как «уведомления сломались», а не как «бот не обновлён».

🔴 **На этой машине рядом работает боевой exit-узел Nivium** (`remnanode`, `caddy-selfsteal`).
Трогать только свои контейнеры, не занимать 80/443.

```bash
# из корня репозитория, на ветке main после мержа
cd "путь к репозиторию"
git checkout main && git pull

tar -czf - -C bot . | ssh root@185.214.10.107 \
  'rm -rf /opt/neuroboost-bot-prod/src && mkdir -p /opt/neuroboost-bot-prod/src && tar -xzf - -C /opt/neuroboost-bot-prod/src'

ssh root@185.214.10.107 'cd /opt/neuroboost-bot-prod && docker compose up -d --build bot'
```

### Что проверить после

```bash
# 🔴 ТОЛЬКО через фильтр: библиотека печатает URL с токеном в открытую
ssh root@185.214.10.107 \
  'docker logs --tail 50 neuroboost-prod-bot 2>&1' \
  | sed -E 's/bot[0-9]+:[A-Za-z0-9_-]+/bot<REDACTED>/g'
```

Ожидание: строки старта без паник. Если в логах `MISSING_TOKEN` или 401 от `/api/svc/*` —
не прописан `SERVICE_TOKEN`, см. `release-checklist` §1.

### Два способа сделать это молча неправильно

1. 🔴 **`docker compose restart` вместо `up -d --build`.** `restart` **не перечитывает `.env`** и
   не пересобирает образ: контейнер продолжает жить со старым кодом и старым окружением, а
   команда отрабатывает успешно. Это стоило суток в Nivium.
2. 🔴 **Не погасить старый контейнер, если бот переезжает.** Два инстанса конкурируют за
   `getUpdates`, Telegram отдаёт апдейт одному из них, и доставка начинает мигать через раз —
   симптом «иногда приходит, иногда нет», который очень трудно связать с причиной.
